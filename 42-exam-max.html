Code final

Version validée — compile avec -Wall -Wextra -Werror, tous tests OK

max.c 
int  max(int* tab, unsigned int len)
{
    unsigned int i = 0;
    if (len == 0)
        return 0;
    int max = tab[i];
    while (i < len)
    {
        if (tab[i] > max)
            max = tab[i];
        i++;
    }
    return (max);
}

2

Flashcards

Clique pour révéler — essaie de répondre dans ta tête AVANT

+
Pourquoi int max = 0 est dangereux ?
Pense aux nombres négatifs...

Si le tableau contient uniquement des négatifs {-5, -3, -1}, aucun élément ne sera > 0, donc on retourne 0 — qui n'est pas dans le tableau. Il faut initialiser avec tab[0].

+
Quelle différence entre while(tab[i]) et while(i < len) ?
String vs tableau d'int...

while(tab[i]) s'arrête quand la valeur vaut 0 — c'est pour les strings (terminées par \0). Un tableau d'int peut contenir des 0 légitimes. Il faut utiliser l'index i < len pour contrôler la boucle.

+
Pourquoi comparer avec max et pas avec tab[i+1] ?
Deux raisons...

1) tab[i+1] déborde quand i est au dernier élément (undefined behavior). 2) Comparer des voisins ne garde pas trace du maximum global — on perd l'info des éléments précédents.

+
Pourquoi unsigned int i et pas int i ?
Le compilateur te le dit...

Comparer un int (signé) avec un unsigned int (non-signé) génère un warning -Wsign-compare. Avec -Werror, ça compile pas. Le compteur doit matcher le type de len.

+
Que se passe-t-il si on lit tab[0] avant de vérifier len == 0 ?
Tableau vide...

Si le tableau est vide (ou NULL), accéder à tab[0] = lecture d'une adresse invalide = segfault ou undefined behavior. Toujours vérifier les cas limites AVANT d'accéder aux données.

Pièges déjoués

7 pièges rencontrés — chaque carte = une leçon gravée

BOUCLE
PIÈGE #1
✕while (tab[i])
✓while (i < len)
Le piège : confondre string (terminée par \0) et tableau d'int (terminé par len). while(str[i]) = strings uniquement.
BOUCLE
PIÈGE #2
✕while (tab[i] < len)
✓while (i < len)
Le piège : confondre valeur et index. tab[i] = ce qu'il y a dans la case. i = quelle case tu regardes.
LOGIQUE
PIÈGE #3
✕max = tab[i]; (sans if)
✓if (tab[i] > max) max = tab[i];
Le piège : écraser l'accumulateur à chaque tour. On update SEULEMENT quand le nouveau est meilleur.
LOGIQUE
PIÈGE #4
✕if (tab[i] < tab[i+1])
✓if (tab[i] > max)
Le piège : comparer des voisins au lieu de l'accumulateur. tab[i+1] = accès hors tableau au dernier élément.
INITIALISATION
PIÈGE #5
✕int max = 0;
✓int max = tab[0];
Le piège : 0 n'est pas neutre pour un max. Avec {-5, -3} on retourne 0 qui n'est pas dans le tableau. Toujours init avec un vrai élément.
SÉCURITÉ
PIÈGE #6
✕int max = tab[i]; // avant check
✓if (len == 0) return 0; // PUIS tab[i]
Le piège : accéder aux données avant de vérifier qu'elles existent. Tableau vide + tab[0] = crash.
TYPE
PIÈGE #7
✕int i = 0; comparé à unsigned int len
✓unsigned int i = 0;
Le piège : -Wsign-compare + -Werror = ça compile pas. Le compteur doit matcher le type de len. Mais l'accumulateur reste int (pour les négatifs).
4

Pattern réutilisable

Parcours + accumulateur — min, max, sum, search, count...

  1. Gérer le cas vide len == 0 en premier
  2. Initialiser l'accumulateur avec tab[0] — jamais avec une valeur arbitraire
  3. Parcourir avec i < len — l'index, pas la valeur
  4. Comparer tab[i] avec l'accumulateur — jamais avec tab[i+1]
  5. Return l'accumulateur

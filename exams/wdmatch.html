wdmatch.c 
#include <unistd.h>

int main(int argc, char **argv)
{
	if (argc != 3)
	{
		write(1, "\n", 1);
		return 0;
	}
	int i = 0;
	int j = 0;
	while (argv[2][i])
	{
		if (argv[1][j] == argv[2][i])
			j++;
		i++;
		if (argv[1][j] == '\0')
		{
			j = 0;
			while (argv[1][j])
			{
				write(1, &argv[1][j], 1);
				j++;
			}
			write(1, "\n", 1);
			return 0;
		}
	}
	write(1, "\n", 1);
	return 0;
}

Flashcards

Réponds dans ta tête AVANT de cliquer

+
Pourquoi la technique des deux pointeurs marche ?
Rôles différents...

i parcourt s2 inconditionnellement (une fois) — c'est la string de référence. j avance seulement quand le char de s1 correspond au char courant de s2. Si j atteint la fin de s1, c'est qu'on a trouvé tous les chars de s1 dans s2 dans l'ordre — par construction.

+
Comment on détecte la fin d'une string en C ?
Terminator...

Toute string C se termine par le caractère null byte : '\0' (valeur ASCII 0). Tester la fin = tester str[i] == '\0' ou son équivalent concis !str[i]. C'est strictement équivalent à while (str[i]) vs while (str[i] != '\0').

+
Pourquoi reset j = 0 avant d'imprimer s1 ?
Réutilisation...

Double usage de j : d'abord curseur de match (avance quand s1[j] == s2[i]), ensuite curseur d'impression pour parcourir s1 et afficher char par char. Économie d'une variable — une seule sert pour deux rôles séquentiels.

+
Si s1 est vide "", que se passe-t-il ?
Match ou pas...

Au premier tour de la boucle, j = 0 et argv[1][0] = '\0' déjà. Le check if (argv[1][j] == '\0') fire immédiatement → on entre dans la branche "print s1". Mais s1 est vide, donc le while (argv[1][j]) ne tourne pas. Seul \n est écrit. Output identique à "no match" — donc peu importe la voie logique prise.

+
Pourquoi argc != 3 en premier ?
Cas limites...

Toujours check les cas limites AVANT d'accéder aux données. Si argc != 3, argv[1] ou argv[2] peuvent être NULL → segfault garanti. Le sujet exige ce comportement défensif et ça sauve de toutes sortes de crashs.

Pièges déjoués

4 pièges — chaque carte = une leçon gravée

RETURN
PIÈGE #1
✕return 0
✓return 0;
Le piège : oublier le point-virgule après return 0 → erreur de compilation. Erreur faite sous pression, facile à repérer dans les premières lignes de gcc.
RETURN FINAL
PIÈGE #2
✕// main se termine sans return
✓write("\n"); return 0; // après le while
Le piège : si on rentre jamais dans la branche "match", le programme doit quand même écrire \n et return 0. Sans return final après le while, comportement Undefined en C (même si gcc force un return 0 par défaut).
CONFUSION i/j
PIÈGE #3
✕while (argv[1][i]) // boucler sur s1
✓while (argv[2][i]) // boucler sur s2
Le piège : c'est s2 (la "source") qu'on parcourt, pas s1. i sur s2, j sur s1. Inversion classique qui fait tout planter silencieusement (pas de warning gcc, juste des tests qui fail).
ORDRE DES STRINGS
PIÈGE #4
✕is_subseq(s2, s1) // s1 contient-il s2 ?
✓is_subseq(s1, s2) // s2 contient-il s1 ?
Le piège : s1 est ce qu'on cherche, s2 est l'endroit où on cherche. Le sujet dit "écrire la première string avec des chars de la seconde" → s1 est le cible, s2 est la source.
4

Pattern réutilisable

Deux pointeurs asynchrones — i avance toujours, j avance conditionnellement

  1. argc != 3 → write \n + return 0
  2. Init i = 0 (curseur s2), j = 0 (curseur s1)
  3. While argv[2][i] (parcours s2 jusqu'au bout) :
    • Si s1[j] == s2[i] → j++ (match)
    • i++ (toujours)
    • Si s1[j] == '\0' → on a tout match → print s1 + \n + return
  4. Après le while : no match total → write \n + return
PATTERN TWO-POINTER ASYNC
wdmatch — s1 est-il sous-séquence de s2 ?
is_subsequence — généralisation (retourne 1/0)
strstr-like — mais pour les sous-séquences, pas les sous-strings
inter/union — même philosophie 2-pointers, conditions différentes
Clé — un pointeur rapide qui parcourt tout, un pointeur lent qui avance seulement quand condition vérifiée

Évolution du code

2 versions — de "logique posée" à "code final"

VERSION 1 — logique posée, pas finie
int main(int argc, char **argv) { if (argc != 3) { write(1, "\n", 1); return 0 // bug: ; manquant } int i = 0; int j = 0; while (argv[2][i]) { if (argv[1][j] == argv[2][i]) j++; i++; } // PAS de return final, PAS de print, PAS de \n }
Logique 2-pointers correcte du premier coup ✓
return 0 sans ; → erreur compilation
Pas de check de fin de match, pas de print, pas de return final
VERSION FINALE ✓ (écrite seul)
while (argv[2][i]) { if (argv[1][j] == argv[2][i]) j++; i++; if (argv[1][j] == '\0') { j = 0; while (argv[1][j]) { write(1, &argv[1][j], 1); j++; } write(1, "\n", 1); return 0; } } write(1, "\n", 1); return 0;
Ajout du check argv[1][j] == '\0' au bon endroit ✓
Double usage de j (match puis print) ✓
Return final + \n pour le cas "no match" ✓
Compile -Wall -Wextra -Werror clean, tous tests OK ✓

Exercices de transfert

Même pattern, exo différent — solidifie l'apprentissage

CHALLENGE 1
inter
Afficher les chars qui apparaissent dans s1 ET s2, dans l'ordre de s1, sans doublons. Utilise le pattern "check si présent" que tu peux dériver de wdmatch.
// "padinton" + "paqefwtdjetytjneytj"
// → "padint"
Indice : pour chaque char de s1, vérifier s'il est dans s2 ET s'il n'a pas déjà été affiché (scanner s1 avant l'index courant).
CHALLENGE 2
union
Afficher les chars qui apparaissent dans s1 OU s2, dans l'ordre d'apparition (s1 d'abord, puis chars nouveaux de s2), sans doublons.
// "zpadinton" + "paqefwtdjety…"
// → "zpadintoqefwjy"
Indice : parcourir s1 puis s2, pour chaque char vérifier s'il a déjà été affiché avant.
CHALLENGE 3
is_subsequence (généralisation)
Même logique que wdmatch, mais la fonction retourne 1 ou 0 au lieu d'imprimer. Utile comme brique de base.
int is_subsequence(char *s1, char *s2);
Indice : identique à wdmatch, mais return (s1[j] == '\0') à la fin — pas besoin de print.

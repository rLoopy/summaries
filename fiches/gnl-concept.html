Pourquoi cette fiche

Le piège de broken_gnl : tu ne peux pas corriger un GNL cassé si tu ne sais pas ce qu un GNL correct DOIT faire. Trouver un bug = comparer le code à un modèle mental. Cette fiche te donne ce modèle.

Bonne nouvelle : 3 des 4 mécanismes de GNL, tu les as déjà vus.

  • static variable → comme le buffer du server minitalk
  • boucle de read → comme read_file dans so_long
  • char * et malloc/strjoin → comme partout dans tes projets
  • le leftover → LE seul nouveau concept (on insiste dessus)

Le contrat de GNL

GNL est appelée plusieurs fois de suite. À chaque appel, elle retourne UNE ligne (avec le \n inclus). Quand le fichier est fini, elle retourne NULL.

// fichier = "abc\ndef\nghi" get_next_line(fd); // retourne "abc\n" get_next_line(fd); // retourne "def\n" get_next_line(fd); // retourne "ghi" (pas de \n final) get_next_line(fd); // retourne NULL (fini)
Le defi : entre 2 appels, GNL doit se souvenir où elle en était dans le fichier. C est le role de la static variable.

Notion 1 — La static variable

Une variable static garde sa valeur entre les appels de la fonction. Sans elle, GNL repartirait de zéro à chaque appel et relirait toujours le début.

static char b[BUFFER_SIZE + 1] = "";
Tu as DEJA vu ca : dans le server minitalk, static unsigned char c gardait le caractere en construction entre les signaux. Meme idee : la static memorise l etat.

Notion 2 — La boucle de read

On ne peut pas lire un fichier d un coup. On lit par bouts de BUFFER_SIZE. On répète read() jusqu à trouver un \n (ou la fin du fichier).

while (pas de \n dans le buffer) { read(fd, buf, BUFFER_SIZE); // lit un bout // accumule dans la ligne }
Tu as DEJA vu ca : dans so_long, read_file bouclait sur read() pour lire toute la map. Meme principe.

Notion 3 — Trouver le \n

On utilise ft_strchr(buffer, '\n') pour savoir si une fin de ligne est présente. Si oui, la ligne se termine là. Si non, il faut lire encore.

a
b
c
\n
d
e
f

strchr trouve le \n (jaune) à la position 3 → la ligne c est "abc\n", le reste "def" c est le leftover.

Notion 4 — Le LEFTOVER (le concept clé)

C est LE truc qui fait rater GNL. Quand on lit par bouts de BUFFER_SIZE, on lit souvent plus qu une ligne. Le surplus (apres le \n) doit etre GARDE pour le prochain appel.

Exemple concret (BUFFER_SIZE = 10)

Fichier : "abc\ndef\nghi"

1er read lit 10 chars d un coup :

a
b
c
\n
d
e
f
\n
g
h
ligne a retourner ("abc\n") le \n trouve LEFTOVER a garder ("def\ngh")

On retourne "abc\n". Mais on a aussi lu "def\ngh" ! Si on jette ce surplus, le prochain appel relit le fichier au mauvais endroit → données perdues.

Le mécanisme du leftover : apres avoir extrait la ligne, on décale le contenu apres le \n vers le debut du buffer static (avec memmove). Comme ca, au prochain appel, le buffer commence par "def\ngh" et on continue proprement.
// apres avoir retourne "abc\n" : ft_memmove(b, tmp + 1, ft_strlen(tmp + 1) + 1); // b contient maintenant "def\ngh" pour le prochain appel
Dans broken_gnl, c est SOUVENT ce qui manque : le code retourne la ligne mais oublie de sauver le leftover. Resultat : le buffer static garde des vieilles donnees ou en perd. Cherche toujours : est-ce que le leftover est gere ?

Notion 5 — Les cas limites

Un GNL correct gère ces situations. Un GNL cassé en oublie souvent :

  • Fin de fichier : read retourne 0 → il faut sortir de la boucle (sinon boucle infinie)
  • Pas de \n final : la derniere ligne sans \n doit quand meme etre retournee
  • Fichier vide : doit retourner NULL direct, pas crasher
  • Plus rien a lire ET buffer vide : retourner NULL (pas une string vide)
  • read retourne -1 (erreur) : retourner NULL
Bug classique #1 : oublier le if (read_ret == 0) break; → boucle infinie en fin de fichier.
Bug classique #2 : la boucle while(!tmp) ne recalcule jamais tmp apres un read → boucle infinie.

Récap — la checklist mentale

Quand tu regardes un GNL (cassé ou pas), verifie ces 5 points :
  1. Static : le buffer survit-il entre les appels ?
  2. Read loop : boucle-t-on bien jusqu au \n, en recalculant la condition ?
  3. Fin de fichier : sort-on de la boucle quand read == 0 ?
  4. Leftover : sauve-t-on le surplus apres le \n pour le prochain appel ?
  5. NULL : retourne-t-on NULL quand il n y a plus rien ?
Prochaine etape : le step debugger visuel, ou tu vois un GNL CORRECT tourner appel par appel. Tu verras le buffer se remplir, la ligne sortir, le leftover rester. Puis on passera aux bugs.

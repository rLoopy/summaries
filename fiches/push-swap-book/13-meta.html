ce que push_swap t'a vraiment appris pour la suite

13.1Ce que push_swap t'a appris

Push_swap n'est pas qu'un projet à valider. C'est un projet charnière qui te donne plusieurs compétences clés pour la suite :

  1. Maîtrise des pointeurs : *, **, &, déréférencement, indirection
  2. Structures dynamiques : linked list, allocation dynamique, gestion mémoire
  3. Architecture de projet : découpage en modules, conventions, makefile
  4. Algorithmes : optimisation, complexité, trade-offs
  5. Tests rigoureux : édge cases, valgrind, automatisation
  6. Defense de code : tu apprends à expliquer ton travail

Ces compétences vont te servir pour tous les projets suivants : philosophers, pipex, minishell, etc.

★ Position de push_swap dans le cursus
Cercle 02 — c'est la "couronne" du cercle 1+2. Pour pouvoir le valider, tu dois avoir solidifié les bases (C, libft, ft_printf, get_next_line). Si tu galères ici, c'est souvent parce qu'une base est friable. Repère laquelle et reviens dessus.

13.2Patterns de pointeurs réutilisables

Pattern 1 : modifier une variable depuis une fonction

Tu l'as vu pour n dans parse_args(argc, argv, &n).

void fct(int *out)
{
    *out = 42;
}

int n;
fct(&n);   // n vaut 42 maintenant

Tu le réutiliseras dans :

  • get_next_line : passer un buffer modifiable
  • pipex : retourner plusieurs valeurs (status, fd, etc.)
  • minishell : passer un environnement, status d'exécution

Pattern 2 : modifier un pointeur depuis une fonction

Le ** de push_swap. Tu l'utilises pour modifier où pointe une variable.

void fct(char **out)
{
    *out = malloc(...);
}

char *s;
fct(&s);   // s pointe maintenant sur l'alloc

Cas d'usage : retourner un pointeur sans utiliser la valeur de retour de la fonction (qui peut être réservée pour un code d'erreur).

Pattern 3 : sentinelle NULL

Le NULL en fin de chaîne. Pattern omniprésent :

  • Linked lists : last->next == NULL
  • argv : argv[argc] == NULL
  • chaînes C : str[len] == '\0'
  • tableaux de chaînes : tokens[n] == NULL

Bouclage type :

while (item != NULL)
{
    // traite item
    item = item->next;  // ou item++ pour les tableaux
}

Réutilisé partout dans le cursus.

13.3Le pattern static helper + wrapper

On l'a utilisé dans op_*.c. Généralisable à plein de situations où tu as N fonctions publiques qui partagent du code.

Squelette type

/* Helper interne, fait le boulot */
static RET do_action(ARGS)
{
    /* logique */
}

/* Wrapper 1 : appelle helper + spécificité 1 */
RET public_a(ARGS)
{
    do_action(args);
    /* spécificité a (ex: write "a\n") */
}

/* Wrapper 2 : appelle helper + spécificité 2 */
RET public_b(ARGS)
{
    do_action(args);
    /* spécificité b */
}

Cas d'usage à venir

  • ft_printf : helper qui gère le formatage, wrappers pour les types (%d, %s, %x...)
  • pipex : helper qui spawn un process, wrappers pour la 1ère commande vs les suivantes
  • minishell : helper qui exécute un AST node, wrappers pour les types (cmd, pipe, redirect...)

Chaque fois que tu te retrouves à copier-coller 2 fonctions presque identiques → static helper + wrappers.

13.4L'art du parcours linked list

Les 4 patterns de parcours que tu as vus :

Pattern 1 : compter / afficher (1 pointeur, stop sur NULL)

node *cur = head;
while (cur)
{
    /* traite cur */
    cur = cur->next;
}

Pour stack_size, is_sorted, print_list...

Pattern 2 : marche au dernier (1 pointeur, stop sur cur->next == NULL)

cur = head;
while (cur->next)
    cur = cur->next;
/* ici cur est le dernier node */

Pour stack_add_bottom, rotate, ajouter à la fin...

Pattern 3 : marche à l'avant-dernier (stop sur cur->next->next)

cur = head;
while (cur->next->next)
    cur = cur->next;
/* ici cur est l'avant-dernier */

Pour reverse_rotate. Plus rare.

Pattern 4 : save-next-then-modify (2 pointeurs)

cur = head;
while (cur)
{
    next = cur->next;       /* sauvegarde AVANT de modifier */
    /* modifie ou détruit cur */
    cur = next;
}

Pour stack_free, et tout ce qui implique de modifier la chaîne pendant qu'on la parcourt.

★ La règle générale
Si tu ne modifies pas la chaîne pendant le parcours → 1 pointeur suffit.
Si tu la modifies (free, déconnecte, etc.) → 2 pointeurs (le 2e sauvegarde l'info dont tu as besoin pour avancer).

13.5Gestion mémoire défensive

Push_swap t'a appris la rigueur mémoire. Les règles à généraliser :

1. Chaque malloc a son free

Tu n'as pas le droit d'allouer sans planifier la libération. Pose-toi la question au moment de l'alloc : "qui va free cette mémoire et quand ?"

2. Check chaque malloc

p = malloc(...);
if (!p)
    /* gérer l'erreur — return, exit, propager */

Pas optionnel. valgrind le détectera, et en peer-eval c'est éliminatoire.

3. Free sur tous les chemins d'erreur

Le pattern qu'on a vu dans convert_tokens : si on alloue puis on rencontre une erreur en milieu de parcours, on free avant de return NULL.

tab = malloc(...);
for (i = 0; i < n; i++)
{
    if (problème)
    {
        free(tab);     /* free avant de quitter */
        return (NULL);
    }
}

4. Set NULL après free

Pour éviter dangling pointers et double-free :

free(ptr);
ptr = NULL;

Surtout important pour les structures partagées entre fonctions.

5. Test avec valgrind avant chaque commit

Pas juste à la fin du projet. À chaque grosse modif. Plus tôt tu détectes une fuite, plus facile à corriger.

13.6Optimisations algorithmiques — quand et comment

Push_swap t'a montré qu'on peut faire bien mieux qu'un algo "naïf" en réfléchissant à la structure du problème.

Principes généraux

  1. Mesurer avant d'optimiser : sans benchmarks, tu optimises à l'aveugle. Notre tester custom permet de mesurer chaque variation.
  2. Trouver le bottleneck : dans push_swap, la phase coûteuse est push_back_to_a à cause des rotations pour amener le max. C'est là qu'on optimiserait en premier.
  3. Trade-offs : chaque optim a un coût (complexité du code, risque de bugs). Choisis celles qui payent.
  4. Simplicité d'abord : tu peux toujours optimiser après. Mais un algo simple et correct est mieux qu'un algo complexe et buggé.

L'astuce de l'indexation

Notre indexation (valeurs → rangs 0..n-1) est un pattern réutilisable : normaliser les inputs dans une plage prévisible. Très utile aussi pour radix sort, hash tables, etc.

La technique de chunking

Découper un problème en paquets et les traiter séquentiellement. Pattern utilisé partout en algorithmique : MapReduce, batching, paginations, etc. Tu le retrouveras.

13.7Pour les projets suivants

philosophers

Projet sur les threads et les mutex. Push_swap t'aide via :

  • Structure des données partagées (struct philo avec pointeurs vers data partagée)
  • Gestion fine de la mémoire (mutex à détruire = équivalent de free)
  • Tests rigoureux (race conditions = bugs subtils)

pipex

Pipes et processus. Réutilise :

  • Le parsing argv (split sur séparateurs, validation)
  • L'allocation et le free conditionnels
  • La gestion d'erreurs avec early returns

minishell

Le gros morceau du cursus. Tu réutiliseras :

  • Linked lists (pour les tokens, les AST nodes, l'env)
  • Parser robuste avec gestion d'erreurs
  • Pattern static helper + wrapper public (pour les builtins, exécutions...)
  • Architecture modulaire (10-15 fichiers comme push_swap)

Les "graphics" (so_long, fdf, fract_ol)

Moins de chevauchement, mais les compétences générales restent :

  • Découper un projet en modules
  • Gérer la mémoire avec MiniLibX
  • Optimiser les boucles de rendu

13.8Erreurs typiques à éviter (dans tous les projets)

ErreurPourquoi c'est mauvaisComment éviter
Allouer sans check de retourCrash silencieux si malloc failToujours if (!p) ... après malloc
Free puis utiliserUse-after-free, comportement indéfiniSet p = NULL après free
Free deux foisDouble-free, crashSet NULL après free, ou ne pas free deux fois
Oublier * ou &Modifications fantômes ou crashRéfléchir au type attendu
Modifier la valeur d'iteration pendant le parcoursBoucle qui rate des éléments ou cycleUtiliser un curseur séparé (cf §13.4)
Variables globalesÉtat partagé invisible, bugs subtilsPasser en paramètre, retourner les résultats
Fonction qui fait trop de chosesDifficile à tester, à maintenir, à réutiliserRefactor en fonctions plus petites (norme 25 lignes aide)
Code dupliqué (copy-paste)Maintenance d'enfer, divergenceExtract en helper static
Pas de testsBugs découverts en peer-eval = 0Test au fur et à mesure, automatise quand possible

13.9Conclusion

★ Ce que tu as construit
Un programme C de ~600 lignes (sans la libft) qui :
  • Parse des arguments arbitraires avec validation rigoureuse
  • Manipule une linked list sans fuite mémoire
  • Implémente 11 opérations complexes sur 2 piles
  • Trie 500 nums en ~7270 ops (un algo qui tient en 50 lignes)
  • Compile sans warning, passe norminette, valgrind clean
  • Validé sur ~3000 cas tests, 0 fail

C'est du vrai code, pas un exercice scolaire. Tu peux en être fier. Et surtout, tu peux maintenant l'expliquer, ce qui est la vraie compétence visée par 42.

Les compétences que tu emportes

  • Lecture et écriture fluides de code C avec pointeurs
  • Compréhension de la mémoire (stack vs heap, malloc, free)
  • Conception d'algorithmes (analyse, complexité, optimisation)
  • Architecture modulaire et conventions de projet
  • Discipline de test et de qualité
  • Capacité à expliquer ton travail

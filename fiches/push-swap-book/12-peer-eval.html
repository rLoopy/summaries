Préparation peer-eval

questions, pitch, defense — pour arriver serein

12.1Le format de la peer-eval

Une peer-eval push_swap dure environ 30-45 min, avec une grille à cocher. Format type :

  1. Vérifications de base (~5 min) : Makefile compile, norminette OK, structure des fichiers
  2. Tests fonctionnels (~10 min) : pas d'arg, déjà trié, doublons, non-int, etc.
  3. Test de tri (~10 min) : 5 nums, 100 nums, 500 nums avec checker_OS
  4. Discussion algorithmique (~10 min) : explique ton algo, pourquoi tu as choisi ça, complexité
  5. Memory check (~5 min) : valgrind, recherche de leaks
  6. Notes : remplir la grille, valider ou non

Les pièges classiques en peer-eval

  • L'évaluateur t'oblige à changer une valeur d'arg et voir si ça marche → teste plusieurs cas
  • L'évaluateur ouvre ton code et demande "explique cette ligne" au hasard → comprends ton code
  • L'évaluateur demande "que se passe-t-il si je passe X" → réfléchis avant de répondre
  • L'évaluateur a un favori = un algorithme particulier (radix, insertion...) → reste solide sur ton choix
⚠ La règle de l'IA
Le sujet impose : "Only use AI-generated content that you fully understand and can take responsibility for". Si tu ne peux pas expliquer une ligne de code, tu peux te faire flag pour "AI fail". Le but de ce gitbook est précisément que tu puisses tout expliquer.

12.2Le pitch en 2 minutes

Quand l'évaluateur arrive, prépare-toi à expliquer ton projet en 2 minutes max. Voilà un script type que tu peux adapter :

★ Le pitch (à apprendre par cœur ou presque)

"Push_swap est un projet de tri sur 2 piles avec 11 opérations limitées. Mon implémentation a 3 niveaux :

  1. Parsing : je valide les arguments (entiers, plage int, doublons) et construis une linked list.
  2. Tris pour petites piles : sort_3 hardcodé sur 6 cas, sort_5 par délégation à sort_3.
  3. Algo Turk pour les grosses piles : j'indexe les valeurs en rangs 0 à n-1, je pousse sur B par chunks (groupes de 16 ou 35 selon n), puis je ramène en sélectionnant le max à chaque étape.

Performance : 100 nums en ~735 ops (validation 80%), 500 nums en ~7270 ops. Norminette OK, valgrind clean. Testé sur ~3000 cas aléatoires avec 4 testers différents, 0 fail."

Si tu as 2 min, dis tout. Si tu as 30 sec, dis juste : "indexation + chunks + max-pull, ~735 ops sur 100 nums, valide 80%".

12.3Questions classiques et réponses

Sur les pointeurs et la struct

Q : Pourquoi tu utilises t_stack ** au lieu de t_stack * dans stack_add_bottom ?
Réponse
"Parce que dans le cas où la pile est vide, je dois modifier la variable head de l'appelant. Si je prenais juste t_stack *, je modifierais une copie locale qui mourrait à la fin de la fonction. Avec **, j'ai l'adresse de la variable head et je peux faire *stack = new pour vraiment changer le head."
Q : Pourquoi tu fais (*stack)->val avec des parenthèses et pas *stack->val ?
Réponse
"C'est une question de priorité d'opérateurs. -> est plus prioritaire que *, donc *stack->val serait interprété comme *(stack->val). Comme stack est t_stack **, il n'a pas de champ val — ça ne compile pas. Avec les parenthèses, je force l'ordre : d'abord déréférencer stack, puis accéder à val."

Sur le parser

Q : Pourquoi tu parses en long via ft_atol au lieu de int ?
Réponse
"Pour détecter les valeurs hors plage int. Si je parsais directement en int, une valeur comme 2147483648 (= INT_MAX + 1) provoquerait un overflow et serait silencieusement convertie en INT_MIN. En long, j'ai une plage beaucoup plus large, donc je parse sans overflow puis je compare aux limites INT_MAX/INT_MIN pour valider."
Q : has_duplicates est en O(n²). Pourquoi tu n'as pas fait un truc plus rapide ?
Réponse
"Pour n ≤ 500, O(n²) = 250 000 comparaisons, soit quelques millisecondes. Pas besoin de plus rapide. Un algo plus subtil (genre hash table) aurait nécessité plus de code et plus d'allocs sans gain pratique pour cette taille. Je préfère la simplicité."

Sur les 11 ops

Q : Pourquoi tu fais un value swap dans sa au lieu d'un pointer swap ?
Réponse
"Parce que c'est plus simple et moins error-prone. sa doit échanger les 2 premiers éléments. Au lieu de recâbler les pointeurs next (4 lignes complexes), j'échange juste les valeurs des 2 nodes avec un tmp (3 lignes). Le résultat visible pour l'utilisateur est identique : top et 2e échangés. Mes nodes restent à leurs adresses originales, seules les valeurs internes bougent."
Q : Explique-moi rotate étape par étape.
Réponse
"5 étapes :
  1. first = *stack — je sauvegarde l'adresse du 1er node parce que je vais le déplacer à la fin
  2. *stack = first->next — j'avance le head d'un cran (le 2e devient le nouveau head)
  3. Je parcours jusqu'au dernier node : last = *stack; while (last->next) last = last->next;
  4. last->next = first — j'attache first derrière le dernier
  5. first->next = NULL — first devient le nouveau dernier, je coupe son ancien lien pour éviter la boucle infinie
"

Sur l'algo Turk

Q : Pourquoi tu indexes les valeurs au début ?
Réponse
"Pour avoir des valeurs dans une plage prévisible [0, n-1]. Sans indexation, je ne saurais pas comment dimensionner mes chunks parce que les valeurs d'entrée peuvent être arbitraires (négatives, énormes, etc.). Avec indexation, je sais que les chunks de 16 vont contenir les rangs 0-15, 16-31, etc. — c'est mécanique."
Q : Explique la formule chunk_max.
Réponse
"chunk_max = (pushed / chunk_size + 1) * chunk_size - 1. Décortiqué :
  • pushed / chunk_size (division entière) = le numéro du chunk en cours
  • + 1 donne le numéro du chunk suivant
  • * chunk_size donne la première valeur du chunk suivant
  • - 1 donne donc la dernière valeur du chunk actuel
Par exemple avec chunk_size = 16 : pushed=10 donne chunk_max=15 (chunk 0). Pushed=20 donne chunk_max=31 (chunk 1). Etc."
Q : Pourquoi tu ramènes le max et pas le min dans push_back_to_a ?
Réponse
"Parce que pa ramène au top de A. Si je ramène les max en premier, ils finissent au bottom de A (les autres viennent par-dessus). Le min sera ramené en dernier et finira au top. Ça donne une pile finale triée croissant comme demandé par le sujet."

Sur la performance

Q : Pourquoi t'es à 80% et pas 100% ?
Réponse
"Pour aller à 100%, il faudrait sub-700 ops pour 100 nums. Je suis à ~735. Pour gagner les 35 ops manquantes, il y a plusieurs optims possibles : tuner chunk_size plus finement, ajouter un rb conditionnel après chaque pb pour pré-trier B, ou réimplémenter une version qui laisse les 3 plus grands sur A pour faire un sort_3 final. J'ai choisi la version 80% pour avoir du code simple, robuste, et facile à expliquer."

12.4Defense de l'usage IA

Le sujet (chapitre V) est explicite : tu peux utiliser de l'IA, mais tu dois pouvoir défendre chaque ligne de ton code. Voici comment présenter ton usage si l'évaluateur pose la question.

★ Position à tenir
"J'ai utilisé l'IA comme assistant pédagogique :
  • Pour expliquer des concepts (pointeurs, algos)
  • Pour générer des squelettes avec TROUs que j'ai remplis moi-même
  • Pour debugger quand je coinçais
  • Pour générer des visualisations HTML qui m'aident à comprendre
Mais chaque ligne de code, je l'ai écrite moi-même ou tapée moi-même, et je peux l'expliquer."

Le README mentionne explicitement

Section "Resources" du README liste :

  • Comment l'IA a été utilisée (pédagogie, debug, visualisations)
  • Que je peux justifier chaque ligne
  • Liens vers les fiches HTML que j'ai construites pour comprendre

Si l'évaluateur le lit, il voit que tu as une démarche réfléchie.

Test ultime : explique-moi cette ligne au hasard

L'évaluateur peut pointer du doigt n'importe quelle ligne et te dire "explique". Avec ce gitbook, tu devrais être capable de :

  • Dire ce que la ligne fait littéralement (lecture syntaxique)
  • Dire pourquoi elle est là (intent)
  • Dire ce qui se passe si on la supprime (conséquence)

Si tu sais répondre à ces 3 niveaux pour chaque ligne, l'évaluateur sera convaincu.

12.5Live coding — modifications demandées

L'évaluateur peut te demander de modifier ton code en live (chapitre IX du sujet). Quelques exemples plausibles :

Ajouter une op

"Ajoute une fonction print_stack(a) qui affiche le contenu de la pile pour debug."

Réponse type :

void print_stack(t_stack *a)
{
    while (a)
    {
        printf("%d ", a->val);
        a = a->next;
    }
    printf("\n");
}

Note : printf est interdit en mandatory, mais pour du debug en live, ça passe (et tu peux mentionner que tu le ferais avec write + conversion en propre).

Changer le format de sortie

"Au lieu d'écrire 'sa\\n', écris 'SA\\n' (en majuscules)."

Tu sais où c'est : dans op_swap.c, ligne du write. Tu changes "sa\n" en "SA\n". Recompile, test. 30 secondes.

⚠ Attention au checker
Si tu fais ce changement, ./checker_OS ne reconnaîtra plus les ops (il attend des minuscules). C'est OK pour une démo "regarde ça compile", mais remets en minuscules avant de retester avec le checker. L'évaluateur attend une simple démo de compilation, pas un test fonctionnel.

Tester un cas particulier

"Tu passes ./push_swap 1 1 1 et tu me dis ce qui se passe."

Réponse : "Le parser détecte les doublons via has_duplicates et retourne NULL. Le main affiche 'Error' sur stderr et exit 1. Aucune ligne sur stdout."

Si l'évaluateur veut le voir : tu le tapes et tu montres.

★ La technique anti-panique
Si l'évaluateur te demande une modif :
  1. Reformule : "Donc tu veux que je fasse XYZ, c'est ça ?"
  2. Identifie le fichier impacté : "C'est dans tel.c"
  3. Réfléchis à voix haute : "Je vais devoir modifier la condition / ajouter une ligne / ..."
  4. Code lentement et lis ce que tu écris
  5. Compile avec make et corrige les warnings éventuels
  6. Teste avec un cas simple
Ne réponds pas en théorie sans vérifier — l'évaluateur veut voir la démarche, pas la perfection.

12.6Cheat sheet finale

★ Les choses à savoir absolument

Architecture

  • 15 fichiers .c, un par responsabilité
  • Pattern static helper + wrapper public dans op_*.c
  • Norme : max 5 fct/fichier, max 25 lignes/fct

Parser

  • tokenize, count_tokens, free_tokens, convert_tokens, parse_args
  • ft_atol parse en long pour détecter overflow
  • has_duplicates en O(n²) — suffisant pour n ≤ 500

Stack

  • t_stack { int val; struct s_stack *next; }
  • ** en paramètre quand on doit modifier le head
  • stack_free : pattern save-next-then-free, *stack = NULL à la fin

Les 11 ops

  • Pattern helper static + wrapper write
  • swap : value swap avec tmp
  • push : 4 étapes (save top, advance src, link dst, set new head)
  • rotate : 5 étapes (save first, advance head, walk to last, attach, first.next=NULL)
  • reverse_rotate : 6 étapes (avant-dernier via cur->next->next)

Algos de tri

  • sort_3 : 6 cas hardcodés, 2 ops max
  • sort_5 : push 2 plus petits sur b, sort_3, pa pa
  • sort_big (Turk) : index_stack → push_to_b → push_back_to_a
  • chunk_size = 16 si n ≤ 100, 35 sinon

Performance

  • 100 nums : max 825, avg 735 → 80%
  • 500 nums : max 7500, avg 7270 → 80%
  • Valgrind clean, norminette OK

Avant la peer-eval, dernière checklist

  • ☐ make compile sans warning
  • ☐ norminette src/ includes/ tout OK
  • ☐ ./push_swap 3 1 2 | ./checker_OS 3 1 2 → "OK"
  • ☐ Valgrind sur quelques cas → 0 leak
  • ☐ Ce gitbook lu en entier
  • ☐ Pitch de 2 min répété 3 fois à voix haute
  • ☐ Code committed et pushé sur le repo 42

Si tous les ☐ sont cochés, tu peux y aller serein. 🚀

Architecture du projet

comment on découpe, pourquoi static+wrapper, le pipeline d'appels

4.1Pourquoi découper en fichiers

Pour push_swap, on a au final 15 fichiers source. Pourquoi pas tout dans un main.c ?

3 raisons

  1. Norminette : max 5 fonctions par fichier. Avec ~50 fonctions, on est obligé de découper.
  2. Lisibilité : un fichier = une responsabilité. parser.c parse, stack.c gère la struct, etc.
  3. Compilation incrémentale : Make ne recompile que les fichiers modifiés. Tu modifies sort_3.c ? Seul sort_3.o est régénéré.

Principe : un fichier = une famille de fonctions

L'idée : chaque fichier regroupe des fonctions liées par leur rôle. Si tu cherches comment fonctionne pa, tu sais qu'elle est dans op_push.c. Si tu veux comprendre sort_3, c'est dans sort_3.c. Pas besoin de fouiller.

★ Anti-pattern à éviter
Mettre tout dans un seul gros fichier "utils.c" avec 20 fonctions sans rapport. C'est l'inverse de la séparation des responsabilités. La norme te force à éviter ça, c'est une bonne chose.

4.2La règle 5 fonctions max

Pour respecter "max 5 fonctions par fichier" tout en exposant un nombre arbitraire de fonctions publiques, on utilise le pattern static helper + wrapper.

Exemple : op_rotate.c

On veut exposer 3 fonctions publiques : ra, rb, rr. Elles font quasiment la même chose (rotate une pile), à part qu'elles écrivent un nom différent sur stdout.

Au lieu de copier-coller le code de rotation 3 fois, on extrait la logique dans un helper static (= visible uniquement dans ce fichier) :

static void rotate(t_stack **stack)
{
    /* logique de rotation : 7 lignes */
}

void ra(t_stack **a)
{
    rotate(a);
    write(1, "ra\n", 3);
}

void rb(t_stack **b)
{
    rotate(b);
    write(1, "rb\n", 3);
}

void rr(t_stack **a, t_stack **b)
{
    rotate(a);
    rotate(b);
    write(1, "rr\n", 3);
}

Bilan : 4 fonctions dans le fichier, dont 1 static + 3 publiques. La norme est OK (≤ 5). DRY est respecté (Don't Repeat Yourself).

★ Avantages du static helper
  • Évite la duplication de code
  • Le helper n'apparaît pas dans le header (pas exporté)
  • Si tu changes la logique de rotation, tu ne modifies qu'un seul endroit
  • La norme compte les fonctions du fichier, pas celles du header

4.4Le pipeline d'appels

Voilà ce qui se passe quand tu lances ./push_swap 3 1 4 1 5, du début à la fin :

1. main reçoit argc=6, argv=["./push_swap", "3", "1", "4", "1", "5"]
↓
2. parse_args(argc, argv, &n)
tokenize → validate → convert → free tokens
retourne int *values = [3,1,4,1,5] et écrit n = 5
↓
3. build_stack(values, n)
crée 5 nodes, retourne le head a
↓
4. free(values)
on n'a plus besoin du tableau, on free
↓
5. if (!is_sorted(a))
évite le tri si déjà ordonné
↓
6. sort(&a, &b)
dispatcher selon stack_size :
1 → rien · 2 → sa · 3 → sort_3 · ≤5 → sort_5 · >5 → sort_big
↓
7. stack_free(&a); stack_free(&b);
libère toute la mémoire heap
↓
8. return 0
★ Pourquoi cet ordre
  • On parse avant de construire : si erreur, on n'a rien à free
  • On free values tôt parce qu'on en a plus besoin une fois la pile construite
  • Le check is_sorted avant sort évite des ops inutiles si la pile arrive déjà triée
  • On free les deux piles à la fin, même si b est censée être vide (au cas où)

4.5Pattern static helper + wrapper public

Pattern fondamental réutilisé dans 5 fichiers (op_swap, op_push, op_rotate, op_reverse, index_stack, push_back_to_a). On formalise :

Quand l'utiliser

  • Plusieurs fonctions publiques font presque la même chose
  • La différence entre elles est mineure (un argument, une action en plus, etc.)
  • On veut éviter la duplication de code
  • On veut respecter la norme (≤ 5 fonctions/fichier)

Comment

/* Helper interne : pas de write, juste la logique */
static void do_action(t_stack **stack)
{
    /* code de l'action */
}

/* Wrapper public 1 : action sur a + write "xx\n" */
void xa(t_stack **a)
{
    do_action(a);
    write(1, "xa\n", 3);
}

/* Wrapper public 2 : action sur b + write "xb\n" */
void xb(t_stack **b)
{
    do_action(b);
    write(1, "xb\n", 3);
}

Pourquoi static ?

Le mot-clé static devant une fonction la rend privée au fichier. Concrètement :

  • Elle n'apparaît pas dans le header (pas exportée)
  • Aucun autre fichier ne peut l'appeler
  • Le compilateur peut l'optimiser plus agressivement (inlining)
  • Pour la norme : ça reste 1 fonction comptée, mais elle est invisible de l'extérieur
★ Confusion possible avec static variable
Attention : static a deux sens en C selon où il est :
  • Devant une fonction ou variable globale : "visible uniquement dans ce fichier" (linkage interne)
  • Devant une variable locale dans une fonction : "garde sa valeur entre les appels" (durée de vie étendue)
Pour nous, c'est toujours le premier sens (devant des helpers).

4.6Le header push_swap.h

Un seul header pour tout le projet. Il contient :

  1. Le header 42 (commentaire en haut)
  2. Les include guards (#ifndef PUSH_SWAP_H)
  3. Les includes externes (libft.h, <limits.h>)
  4. La struct t_stack
  5. Les prototypes de toutes les fonctions publiques, groupés par famille

Structure

#ifndef PUSH_SWAP_H
#define PUSH_SWAP_H

/* includes */
#include "libft.h"
#include <limits.h>

/* struct */
typedef struct s_stack
{
    int              val;
    struct s_stack  *next;
}   t_stack;

/* PARSER */
long    ft_atol(char *s);
int     is_valid_int(char *s);
/* ... */

/* STACK */
t_stack *stack_new(int val);
void    stack_add_bottom(t_stack **stack, int val);
/* ... */

/* OPS */
void    sa(t_stack **a);
/* ... les 11 ops ... */

/* SORT */
void    sort(t_stack **a, t_stack **b);
/* ... */

#endif
★ Les helpers static ne sont PAS dans le header
Les fonctions static ne doivent pas apparaître dans le header. C'est leur but : rester privées au fichier source. Si tu mets le prototype dans le header, ça défait l'intérêt et le compilateur warn.

Les include guards

#ifndef PUSH_SWAP_H
#define PUSH_SWAP_H
/* tout le contenu du header */
#endif

Si plusieurs fichiers .c incluent ce header, sans guards on aurait des redéfinitions de t_stack et erreurs de compilation. Les guards garantissent que le contenu n'est inclus qu'une fois par unité de compilation.

4.7Le Makefile

Le Makefile orchestre la compilation. Structure type :

NAME      = push_swap

CC        = cc
CFLAGS    = -Wall -Wextra -Werror

SRC_DIR   = src
OBJ_DIR   = obj
INC_DIR   = includes
LIBFT_DIR = libft

LIBFT     = $(LIBFT_DIR)/libft.a

SRCS      = $(SRC_DIR)/main.c \
            $(SRC_DIR)/parser.c \
            $(SRC_DIR)/validator.c \
            # ... etc

OBJS      = $(SRCS:$(SRC_DIR)/%.c=$(OBJ_DIR)/%.o)
INCLUDES  = -I$(INC_DIR) -I$(LIBFT_DIR)

all:      $(NAME)

$(NAME):  $(LIBFT) $(OBJS)
          $(CC) $(CFLAGS) $(OBJS) -L$(LIBFT_DIR) -lft -o $(NAME)

$(LIBFT):
          $(MAKE) -C $(LIBFT_DIR)

$(OBJ_DIR)/%.o: $(SRC_DIR)/%.c | $(OBJ_DIR)
          $(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@

$(OBJ_DIR):
          mkdir -p $(OBJ_DIR)

clean:
          rm -rf $(OBJ_DIR)
          $(MAKE) -C $(LIBFT_DIR) clean

fclean:   clean
          rm -f $(NAME)
          $(MAKE) -C $(LIBFT_DIR) fclean

re:       fclean all

.PHONY:   all clean fclean re

Concepts clés du Makefile

ÉlémentRôle
$(NAME)nom de l'exécutable final, ici push_swap
$(SRCS)liste de tous les .c à compiler
$(OBJS)liste des .o (générés depuis SRCS via la règle de substitution)
$(LIBFT)la libft à compiler en premier
.PHONYcibles qui ne créent pas de fichier (pour que make ne se trompe pas)
$<variable Make qui désigne le 1er prérequis (= le .c source)
$@variable Make qui désigne la cible (= le .o à produire)

Les règles obligatoires (norme)

  • all : compile le projet
  • clean : supprime les .o
  • fclean : clean + supprime l'exécutable
  • re : fclean puis all
  • $(NAME) : la cible principale
⚠ Pas de relink inutile
Le sujet exige qu'on ne fasse pas de relink quand rien n'a changé. C'est garanti naturellement par les dépendances sur les .o (et le timestamp). Si tu utilises make deux fois de suite sans modifier de fichier, la 2e fois doit dire "`push_swap' is up to date".

4.8Récap du chapitre

★ L'architecture en bref
  1. 15 fichiers .c, un par responsabilité.
  2. 1 header push_swap.h avec tous les prototypes publics + struct t_stack.
  3. Pattern récurrent : static helper interne + wrappers publics qui ajoutent le write.
  4. Norme : max 5 fonctions/fichier, max 25 lignes/fct.
  5. Pipeline : main → parse_args → build_stack → sort → stack_free.
  6. Makefile avec règles obligatoires all/clean/fclean/re, flags -Wall -Wextra -Werror, sans relink.
  7. Le check is_sorted avant sort évite les ops inutiles si déjà trié.
Auto-éval
Pourquoi on met les helpers en static ?
Pour les cacher des autres fichiers (linkage interne). Ils n'apparaissent pas dans le header, le compilateur sait qu'ils ne sont utilisés que localement, et c'est plus propre. Bonus : pour la norme, on a quand même droit à 5 fonctions par fichier mais les statics restent invisibles de l'extérieur.
Pourquoi on free values juste après build_stack ?
Parce que values (le tableau d'int) n'est plus utile une fois que la pile a est construite : les valeurs ont été copiées dans les nodes. Libérer tôt = pas de mémoire qui traîne. Plus tu free tôt, plus tu réduis le risque d'oublier.
Quelle est la différence entre les règles clean, fclean, et re ?
clean : supprime juste les objets (.o et dossier obj/).
fclean : clean + supprime aussi l'exécutable push_swap.
re : fclean + all = rebuild complet depuis zéro.

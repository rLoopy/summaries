Le pipeline complet

main ligne par ligne, gestion d'erreurs, cleanup

10.1Le code main.c complet

static int print_error(void)
{
    write(2, "Error\n", 6);
    return (1);
}

int main(int argc, char **argv)
{
    int     n;
    int     *values;
    t_stack *a;
    t_stack *b;

    if (argc < 2)
        return (0);
    values = parse_args(argc, argv, &n);
    if (!values)
        return (print_error());
    a = build_stack(values, n);
    free(values);
    if (!a)
        return (print_error());
    b = NULL;
    if (!is_sorted(a))
        sort(&a, &b);
    stack_free(&a);
    stack_free(&b);
    return (0);
}

21 lignes au total (avec les déclarations et l'helper), tout compris. C'est le squelette qui orchestre les ~15 autres fichiers.

10.2Le helper print_error

static int print_error(void)
{
    write(2, "Error\n", 6);
    return (1);
}

Pourquoi ce helper ?

Pour respecter la norme : main a 2 cas d'erreur, chacun avec 2 actions (write + return). Sans helper, on aurait :

if (!values)
{
    write(2, "Error\n", 6);
    return (1);
}
// ...
if (!a)
{
    write(2, "Error\n", 6);
    return (1);
}

main passerait à 26+ lignes → dépassement de la limite de 25 (norminette). Avec le helper, chaque cas tient en 1 ligne :

if (!values)
    return (print_error());
if (!a)
    return (print_error());

Compact, DRY, conforme à la norme.

Pourquoi static ?

Parce que print_error n'a aucune raison d'être appelée depuis un autre fichier. Le mot-clé static la garde locale à main.c.

Pourquoi return (1) ?

Pour que main retourne 1 à l'OS = "exit code non-zero = il y a eu une erreur". Convention Unix. Quand tu fais ./push_swap abc; echo $?, tu obtiens 1.

10.3Les early returns

Le code de main utilise des "early returns" : sortir tôt en cas de problème, sans imbriquer des if/else profonds.

Les 3 early returns

if (argc < 2)
    return (0);                  // pas d'arg → exit 0 silencieux

// ...

if (!values)
    return (print_error());        // parser a échoué → Error + exit 1

// ...

if (!a)
    return (print_error());        // build_stack a échoué (malloc) → Error + exit 1

Avantages du pattern early return

  • Code linéaire, facile à lire
  • Pas d'indentation profonde (chaque condition → un return)
  • Le "happy path" (= tout va bien) reste en bas, lisible
  • Pas de variables d'état d'erreur à propager
★ Pattern alternatif (qu'on n'utilise PAS)
int ret = 0;
if (argc < 2)
{
    // rien
}
else
{
    values = parse_args(...);
    if (!values)
    {
        ret = 1;
        // ...
    }
    else
    {
        // suite
    }
}
return (ret);
Imbrication profonde → lourd à lire. Les early returns sont plus propres pour un flow comme celui-ci.

10.4Le flow ligne par ligne

On déroule chaque ligne dans l'ordre.

Lignes 1-5 : déclarations

int     n;
int     *values;
t_stack *a;
t_stack *b;

Norme : déclarations en début de fonction, séparées du code par une ligne vide. Pas d'initialisation directe (la norme préfère x; puis x = ...;).

Ligne 6 : check argc

if (argc < 2)
    return (0);

Si l'user n'a pas passé d'argument, on sort immédiatement (silencieusement). Le sujet impose ce comportement.

Ligne 7-8 : parsing

values = parse_args(argc, argv, &n);
if (!values)
    return (print_error());

On appelle parse_args (cf Ch. 05). Si ça échoue (NULL retourné), on affiche Error et on sort avec code 1.

Note bien le &n : on passe l'adresse de n pour que parse_args puisse écrire la taille via *n = ....

Ligne 9-12 : construction de la pile

a = build_stack(values, n);
free(values);
if (!a)
    return (print_error());

On convertit le tableau d'int en linked list. Une fois la pile construite, on n'a plus besoin du tableau intermédiaire → on free.

Si build_stack échoue (malloc out of memory), on sort avec Error. C'est un cas extrême mais on le gère pour ne jamais avoir de comportement indéfini.

Ligne 13 : init de b

b = NULL;

La pile b commence vide. NULL est la représentation d'une linked list vide.

Ligne 14-15 : le tri

if (!is_sorted(a))
    sort(&a, &b);

Optimisation : si la pile arrive déjà triée, on évite tout le travail. Sinon, on lance sort qui dispatche selon la taille (cf Ch. 08).

Lignes 16-18 : cleanup

stack_free(&a);
stack_free(&b);
return (0);

On libère les 2 piles (même si b devrait être vide à ce stade — au cas où). Exit avec code 0 (= succès).

10.5Le cleanup — détail critique

Toutes les allocs

Dans le flow, on a 3 types d'allocations potentielles :

  1. parse_args alloue le tableau values (et internement des tokens qu'elle free elle-même)
  2. build_stack alloue n nodes via stack_new
  3. Les opérations de tri (pb, pa) déplacent les nodes existants mais n'allouent rien
  4. index_stack (si on passe par sort_big) alloue temporairement un tableau qu'elle free elle-même

Les frees correspondants

  1. free(values) après build_stack
  2. stack_free(&a) et stack_free(&b) à la fin de main

Chaque alloc a son free. Vérifié avec valgrind : 0 byte en fuite.

Pourquoi free b même si elle est vide

À la fin du tri normal (Turk), b doit être vide. Mais :

  • Si l'algo de tri a un bug et laisse des éléments → stack_free les libère
  • stack_free sur une pile vide est sûr (ne fait rien)
  • Ça met la variable b à NULL proprement

C'est une protection à coût zéro qui rend le code robuste.

Le passage par &a

On passe &a à stack_free (pas juste a) parce que stack_free met *stack = NULL à la fin → modifie la variable locale a de main. C'est juste pour la propreté du pointeur après free.

10.6Tracer un exemple complet

Suivons ./push_swap 3 1 2 de bout en bout.

Étape 1 : entrée dans main

argc = 4 argv = ["./push_swap", "3", "1", "2", NULL]

Étape 2 : check argc

argc < 2 ? 4 < 2 ? NON → on continue.

Étape 3 : parse_args

parse_args(4, argv, &n) :

  • tokenize → ["3", "1", "2", NULL]
  • count_tokens → 3, écrit dans n
  • convert_tokens : check chaque, convert → values = [3, 1, 2]
  • has_duplicates → 0 (pas de doublon)
  • return values

Retour : values = [3, 1, 2], n = 3.

Étape 4 : build_stack

a = build_stack([3, 1, 2], 3) :

  • add_bottom(3) → a = [3]
  • add_bottom(1) → a = [3, 1]
  • add_bottom(2) → a = [3, 1, 2]
  • return head

Pile a contient les nodes pour 3, 1, 2.

Étape 5 : free(values)

Le tableau d'int n'est plus utile. On le libère.

Étape 6 : b = NULL

Pile b commence vide.

Étape 7 : is_sorted(a)

Parcourt [3, 1, 2] : 3 > 1 → return 0 (pas trié). Le if match.

Étape 8 : sort(&a, &b)

Dispatcher : stack_size(*a) = 3 → branche sort_3(a).

sort_3 lit top=3, mid=1, bot=2. Test :

  • top < mid && mid < bot ? 3 < 1 ? NON
  • top > mid && top < bot ? 3 > 1 ✓, 3 < 2 ? NON
  • top > mid && top > bot && mid < bot ? 3 > 1 ✓, 3 > 2 ✓, 1 < 2 ✓ → MATCH

Action : ra(a). Écrit "ra\n" sur stdout. Modifie la pile : a = [1, 2, 3].

Étape 9 : stack_free(&a) + stack_free(&b)

Libère les 3 nodes de a. b est déjà vide → no-op. a et b sont mis à NULL.

Étape 10 : return 0

Le processus termine avec exit code 0.

Sortie observée par l'user

$ ./push_swap 3 1 2
ra
$ echo $?
0

1 ligne sur stdout (ra), exit 0. Sortie minimaliste, conforme au sujet.

10.7Récap du chapitre

★ Le pipeline en 7 étapes
  1. Check argc : 0 arg → exit 0 silencieux
  2. parse_args → int *values + n, ou NULL si erreur
  3. build_stack → t_stack *a
  4. free(values) (plus utile)
  5. Initialiser b = NULL
  6. Check is_sorted, sinon sort(&a, &b)
  7. stack_free(&a) + stack_free(&b), exit 0
★ Hygiène mémoire
  • Chaque alloc est trackée et freed
  • Early returns avec cleanup propre (ou via les fonctions appelées)
  • Helper print_error pour économiser des lignes
  • valgrind : 0 leak, 0 erreur
Auto-éval
Pourquoi free(values) après build_stack et pas à la fin ?
Parce que values n'est plus utile après build_stack (ses valeurs ont été copiées dans les nodes). Free tôt = pas de mémoire orpheline qui traîne longtemps. C'est aussi plus facile à raisonner : tant que tu ne touches plus à une variable, tu peux la free.
Que retourne main dans chacun des cas ?
  • Pas d'argument → return 0 (succès, rien à faire)
  • Parse erreur → return print_error() = return 1
  • build_stack erreur → idem
  • Tri réussi → return 0
0 = succès, 1 = erreur. Convention Unix standard.
Pourquoi on appelle stack_free(&b) alors que b devrait être vide ?
Robustesse. Si pour une raison quelconque b n'est pas vide (bug, optimisation future), stack_free nettoie. Et c'est sûr sur une pile vide (ne fait rien). Coût zéro, sécurité totale.

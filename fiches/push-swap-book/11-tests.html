Tests & qualité

comment on a validé que ça marche dans tous les cas

11.1Pourquoi tester rigoureusement

Push_swap n'est pas un projet où "ça compile et ça marche sur 3 cas" suffit. Tu seras évalué sur :

  • La norme : 0 si non respectée
  • Les memory leaks : 0 si présents
  • Les crashes : 0 si segfault
  • Les benchmarks : note proportionnelle au nombre d'ops

Une erreur dans n'importe lequel de ces points = note diminuée ou 0 net. Donc on teste à fond.

Les 4 couches de test

  1. Custom tester Python : simule les ops, vérifie le tri, compte les ops
  2. Testers communautaires : LeoFu, gemartin99, SimonCROS — confirment notre simulation
  3. Valgrind : zéro leak, zéro accès invalide
  4. Norminette : conformité au style 42

11.2Le tester custom Python

On a écrit tester.py sur le VPS qui :

  1. Génère N entiers aléatoires
  2. Lance ./push_swap avec ces entiers
  3. Lit la sortie (les ops affichées)
  4. Simule ces ops sur la pile initiale
  5. Vérifie que la pile finale est triée
  6. Compte les ops, calcule min/avg/max sur N runs

Pourquoi un simulateur en Python ?

Parce qu'on n'a pas checker_OS sur le VPS (il est sur l'intranet 42 uniquement). On reproduit son comportement en Python. Comme les 11 ops sont déterministes et publiques, notre simulateur est équivalent fonctionnel au checker officiel.

Le cœur du simulateur

def simulate(initial, ops):
    a, b = list(initial), []
    for op in ops:
        op = op.strip()
        if op == 'sa' and len(a) >= 2:
            a[0], a[1] = a[1], a[0]
        elif op == 'pa' and b:
            a.insert(0, b.pop(0))
        elif op == 'pb' and a:
            b.insert(0, a.pop(0))
        elif op == 'ra' and a:
            a.append(a.pop(0))
        elif op == 'rra' and a:
            a.insert(0, a.pop())
        # ... etc pour les 11 ops
    return a, b

Liste Python comme pile, opérations équivalentes. Si on a écrit nos ops C correctement, la simulation Python doit produire le même résultat final.

Usage

$ python3 tester.py
==================================================
  Benchmark : 100 nums × 20 runs
==================================================
  ✓ Tous OK (20/20)
  ops : min=688  avg=729.1  max=772
  ✓ 80%  : <1100 ops

Résultats sur ~1400 cas

  • 3 nums : 50/50 OK
  • 5 nums : 50/50 OK
  • 100 nums : 200/200 OK
  • 500 nums : 200/200 OK

Statistiquement, on est très confiants.

11.4Valgrind — zéro leak

Valgrind est un outil qui exécute ton programme dans un environnement instrumenté et détecte :

  • Les memory leaks (mémoire allouée non libérée)
  • Les accès invalides (déréférencement NULL, use-after-free, etc.)
  • Les lectures non initialisées

Usage

$ valgrind --leak-check=full ./push_swap 3 1 4 1 5
ra
sa
pb
...
==12345== HEAP SUMMARY:
==12345==     in use at exit: 0 bytes in 0 blocks
==12345==   total heap usage: 6 allocs, 6 frees, 64 bytes allocated
==12345== All heap blocks were freed -- no leaks are possible
==12345== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)

Ce qu'il faut vérifier

  • in use at exit: 0 bytes ← obligatoire (sinon leak)
  • ERROR SUMMARY: 0 errors ← obligatoire (sinon segfault potentiel)
  • total heap usage : équilibré (autant d'allocs que de frees)

Edge cases testés

On a passé valgrind sur :

  • Pas d'arg : OK, 0 alloc
  • Pile triée [1,2,3] : OK, 0 leak
  • Reverse [5,4,3,2,1] : OK
  • Doublons [1,2,1] → Error : OK, free correct
  • Non-nombre [1,abc] → Error : OK, free correct
  • INT_MAX, INT_MIN : OK
  • 500 nums random : OK, <100ms

0 leak, 0 erreur sur tous les cas.

11.5Norminette

La norminette est l'outil officiel 42 qui vérifie le style C. Si elle dit "Error", c'est 0 net au projet.

Les règles principales

  • Max 25 lignes par fonction (entre les accolades)
  • Max 5 fonctions par fichier
  • Max 5 déclarations par fonction
  • Max 4 paramètres par fonction
  • Lignes < 80 colonnes
  • Header 42 obligatoire en haut de chaque fichier
  • Pas de // commentaires, uniquement /* */
  • Pas de commentaires inline après code (sauf en début de bloc ou avant fonction)
  • Pas de ligne vide à l'intérieur d'une fonction (sauf après les déclarations)
  • Pas de printf, atoi, etc. en dehors de la libft autorisée
  • Pas de variables globales
  • Indentation par tab (4 chars), pas d'espaces

Usage

$ norminette src/ includes/
src/main.c: OK!
src/parser.c: OK!
src/stack.c: OK!
... (tous les fichiers OK)

Les erreurs qu'on a rencontrées et corrigées

11.7Récap

★ Les 4 piliers de la qualité
  1. Tester custom : 1400 cas simulés, 0 fail
  2. 3 testers communautaires : LeoFu, gemartin, SimonCROS — 0 fail combiné
  3. Valgrind : 0 leak, 0 erreur sur tous les edge cases
  4. Norminette : tous fichiers OK
★ La discipline du test
On a testé à chaque étape du développement, pas juste à la fin. Quand on a ajouté sort_3, on a immédiatement testé les 6 permutations. Quand on a écrit push_to_b, on l'a testé. C'est ce qui permet d'attraper les bugs tôt — comme l'invariant cassé dans la version initiale de Turk (Ch. 09 §9.8).
Auto-éval
Pourquoi un simulateur Python plutôt que checker_OS direct ?
checker_OS n'est pas sur notre VPS (intranet 42 seulement). Le simulateur Python reproduit son comportement (les ops sont publiques et déterministes). Avantage : on peut le lancer en boucle sur 1000 cas pour avoir des stats fiables.
Que signifie "in use at exit: 0 bytes" dans la sortie valgrind ?
Qu'à la fin du programme, aucune mémoire allouée n'est restée. Tous les malloc ont été équilibrés par des free. C'est le but visé : 0 byte en fuite.
Si norminette dit "Error" sur un seul fichier, que se passe-t-il en peer-eval ?
Le projet est noté 0 net. La norme est une contrainte non-négociable. C'est pour ça qu'on a passé la norminette avant tout le reste.

le manuel qui te rend imbattable en peer-eval

§Pourquoi ce gitbook

★ 2 modes de lecture
Avant d'avoir codé push_swap : lis dans l'ordre, du Ch 01 au Ch 13. Le code montré dans les chapitres est la version cible — ce que tu vas construire toi-même. Quand tu lis "on a fait X" ou "notre code", lis-le comme "voici ce que tu vas faire". Les chapitres te guident concept par concept jusqu'à ce que tu sois prêt à écrire ton code.

Après avoir codé : utilise le manuel comme révision pour la peer-eval. Le Ch 12 est ton allié pour les questions classiques.

Le manuel reprend chaque concept depuis le bas (oui, depuis "qu'est-ce qu'une adresse mémoire") et te mène jusqu'à l'algo Turk. L'objectif :

  • Comprendre pourquoi chaque morceau existe
  • Savoir défendre chaque choix en peer-eval
  • Construire des réflexes réutilisables pour les projets suivants (philosophers, pipex, minishell…)
★ Quand consulter les fiches animées
Le gitbook référence des fiches HTML animées (rotate step-by-step, Turk simulateur, etc.) — liens en bas de page sous "Annexes". Ouvre-les quand tu sens que ça coince sur un concept précis. Elles complètent le texte mais ne le remplacent pas.
★ Prérequis honnête
Ce manuel se veut accessible mais suppose que tu as fait libft (ou que tu as touché aux bases : int main, argc/argv, malloc, différence .c / .h, compilation avec gcc). Si tu n'as jamais écrit une ligne de C, fais d'abord libft — c'est la marche obligatoire. Sinon le Ch 03 (norme + Makefile) et le Ch 04 (architecture) iront trop vite.
★ Comment lire
Lis dans l'ordre la première fois (les chapitres se construisent les uns sur les autres). Pour les revisions, utilise le sommaire à gauche pour sauter sur ce qui te bloque. Chaque chapitre se termine par un récap et une auto-évaluation.

§Glossaire — les mots techniques à connaître

Une référence rapide pour les termes flous qui reviennent dans le gitbook. Si un mot t'arrête dans un chapitre, viens checker ici.

MotDéfinition simpleVu en Ch.
adresse mémoirenuméro de casier en RAM où vit une variable01
déréférencer"suivre un pointeur" pour atteindre la valeur pointée (via *p)01
comportement indéfinicode qui peut crasher, marcher par hasard, ou faire n'importe quoi — résultat imprévisible. À éviter à tout prix.01
stack vs heapstack = mémoire auto, courte durée ; heap = mémoire malloc, longue durée01
hexadécimal (0x...)notation pour écrire les adresses : 0x10 = 16, 0xFF = 255, 0x100 = 25601
big-O (O(n), O(n²))notation de complexité : O(n) = travail proportionnel à n ; O(n²) = travail = n×n. Utilisé pour dire "ça va vite" ou "ça va lentement"02
sentinellevaleur spéciale qui marque la fin (ex: NULL en bout de chaîne, \0 en fin de string)02
fd (file descriptor)numéro qui identifie une "destination de sortie". fd=0 = clavier (stdin), fd=1 = écran (stdout), fd=2 = erreurs (stderr). Utilisé dans write(fd, ...)03
stdout / stderrsorties standard : stdout (fd 1) pour les ops, stderr (fd 2) pour les erreurs03
static (devant fonction)fonction visible uniquement dans son fichier .c (pas exportée). On dit "linkage interne"04
linkagerègle qui définit qui peut "voir" une fonction. Interne = juste le fichier, externe = tout le projet04
castconversion explicite de type, ex: (int)x dit "traite x comme un int". À utiliser avec précaution (perte d'info possible)05
tokeniserdécouper une chaîne en morceaux selon un séparateur. ft_split tokenise sur les espaces05
helper static + wrapperpattern : 1 fonction interne fait le travail, plusieurs fonctions publiques l'appellent avec des spécificités. Permet de respecter "5 fonctions max par fichier"04, 07
pointer jugglingmanipulation acrobatique de plusieurs pointeurs avec risque élevé de bug (à éviter quand possible — préférer value swap)07
invariantcondition qui doit rester vraie tout au long de l'algo. Ex: dans sort_5, "valeurs sur b < valeurs sur a"08
radix sorttri par chiffres successifs. L'algo Turk s'en inspire (groupes par rang)09
checker (checker_OS)binaire fourni par 42 qui exécute tes ops sur la pile et te dit "OK" ou "KO"03, 11
valgrindoutil qui détecte les memory leaks et les accès mémoire invalides11
norminetteoutil officiel 42 qui vérifie le style C. Si erreur → 0 au projet03, 11
singly linked listchaîne où chaque node a uniquement un pointeur next vers le suivant. Pas de prev. C'est ce qu'on utilise.02
doubly linked listchaîne où chaque node a next ET prev. Plus flexible mais plus lourd. Inutile pour push_swap.02
paddingoctets de remplissage que le compilateur ajoute dans une struct pour aligner les champs en mémoire. Invisible pour toi, mais explique pourquoi sizeof(t_stack) = 16 et pas 12.01, 02
dangling pointer"pointeur fantôme" — pointeur qui pointe sur de la mémoire déjà libérée. Lire/écrire dessus = UB. Mettre à NULL après free pour s'en protéger.01, 06
double-freeappeler free() deux fois sur le même pointeur. Crash immédiat. Évité en mettant le pointeur à NULL après le premier free (free(NULL) est légal).06
memory leakmémoire allouée qui n'est jamais freed. S'accumule jusqu'à saturer la RAM. Détecté par valgrind.01, 06

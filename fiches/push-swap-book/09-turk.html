9.1Le problème : trier 100+ nums en moins de 700 ops

Pour les piles > 5, on ne peut plus hardcoder. Il nous faut un algorithme qui tienne compte des contraintes du sujet :

  • Seulement 11 opérations possibles
  • Pas d'accès aléatoire (pas de arr[i])
  • Budget serré : 100 nums en moins de 700 ops pour la validation 100 %

Un sorting algo "normal" (insertion sort) coûterait combien ?

Pour 100 nums avec insertion sort sur 2 piles, l'analyse donne ~5000 ops en moyenne. Très loin du budget de 700. Il faut une approche plus maline.

Le défi spécifique

Tu ne peux pas comparer 2 éléments arbitraires. Tu ne peux comparer que :

  • Le top de a avec le 2e de a (via sa conditionnelle)
  • Le top de a avec le top de b (via pa/pb)
  • Aucune comparaison directe entre 2 éléments quelconques

Donc tu fais du tri "à l'aveugle" pour la plupart des éléments. Cette contrainte est ce qui rend push_swap difficile.

9.2Pourquoi pas un algo classique

Insertion sort sur 2 piles

  1. Pour chaque élément de a :
    • Trouver sa place dans b (qui contient les éléments déjà triés)
    • Faire les rotations nécessaires sur b pour aligner
    • Push depuis a vers b

Complexité estimée : O(n²) ops pour n éléments → ~10 000 ops pour 100 nums. Loin du budget.

Quicksort sur linked list

Difficile à implémenter sur linked list car pas d'accès indexé. Demande beaucoup de manipulations. Pas adapté au modèle 11-ops.

Radix sort

Radix sort fonctionne par "chiffres" successifs et est efficace pour les entiers. Coût : ~n × log₂(max_val). Mais nécessite des passes successives et de la mémoire auxiliaire.

L'algo Turk est inspiré du radix mais adapté à 2 piles, et utilise une indexation qui rend la complexité prédictible.

9.3L'idée des chunks

L'intuition

Au lieu de pousser 1 élément à la fois (insertion sort) ou de tout pousser puis revenir (naïf), on pousse les éléments par paquets (chunks) selon leur valeur.

Exemple sur 100 nums :

  • Chunk 0 : les 16 plus petits valeurs (rangs 0-15)
  • Chunk 1 : les 16 suivants (rangs 16-31)
  • Chunk 2 : 32-47
  • ... etc.

On parcourt a et :

  • Si l'élément actuel appartient au chunk en cours → pb (push sur b)
  • Sinon → ra (skip, on s'en occupera plus tard)

À la fin de chaque chunk, on passe au suivant. Quand tout est sur b, on ramène en sélectionnant les plus grands d'abord pour que la pile finale soit triée.

Pourquoi cette stratégie est efficace

  • Chaque élément est pushé une fois et repushé une fois → ~2n ops de push minimum
  • Plus quelques rotations pour les positionner → ~3-5n au total
  • Pour 100 nums : ~500-700 ops, dans le budget

La taille du chunk est un paramètre crucial. Trop petit = beaucoup de rotations. Trop grand = pas assez de structure sur b. On verra le choix optimal.

★ Origine du nom "Turk"
L'algo doit son nom à un étudiant de 42 qui a popularisé cette approche pour push_swap. Il n'a rien à voir avec un algo académique standard — c'est un classique du folklore push_swap.

9.3bWalk-through complet sur 8 nums

Avant de plonger dans le code, déroulons Turk sur un exemple concret pour avoir l'intuition. On prend ./push_swap 42 7 99 13 5 60 25 88 et on suit les 3 phases.

Phase 1 — Indexation (val → rang)

On remplace chaque valeur par son rang (0 = plus petit, 7 = plus grand). Pour calculer les rangs, on trie mentalement la liste :

Tri mental : 5 → rang 0 7 → rang 1 13 → rang 2 25 → rang 3 42 → rang 4 60 → rang 5 88 → rang 6 99 → rang 7 Avant : a = [42, 7, 99, 13, 5, 60, 25, 88] b = [] Après : a = [ 4, 1, 7, 2, 0, 5, 3, 6] b = []

Maintenant les valeurs sont dans [0, 7]. On peut définir des chunks proprement.

Phase 2 — push_to_b avec chunk_size = 3 (pour la démo)

On a 8 nums, target = 8 (on pousse tout). chunk_size = 3 (juste pour cette démo ; en vrai c'est 16). Les chunks couvrent : chunk 0 = rangs 0-2, chunk 1 = 3-5, chunk 2 = 6-7.

★ Ce qui se passe en gros

  2. Phase 2 distribue ces rangs sur b par chunks → structure approximativement décroissante

9.4Phase 1 : index_stack — val → rang

Pourquoi indexer ?

Les valeurs initiales sont arbitraires : [42, -3, 1500, 7, ...]. On ne sait pas à priori dans quel "chunk" elles appartiennent (chunk 0 = les 16 plus petites de QUOI exactement ?).

Solution : on remplace chaque valeur par son rang dans la pile triée.

// Avant
a = [42, -3, 1500, 7]

// Après index_stack
a = [2, 0, 3, 1]

// Le 42 est le 3e plus petit (rang 2), -3 est le plus petit (rang 0), etc.

Maintenant on sait que les rangs vont de 0 à n-1. Chunks bien définis :

  • Chunk 0 : rangs 0 à 15 (les 16 plus petits)
  • Chunk 1 : rangs 16 à 31
  • ... etc.

Le code index_stack

int index_stack(t_stack *a)
{
    int     n;
    int     *vals;
    t_stack *cur;

    n = stack_size(a);
    vals = malloc(sizeof(int) * n);
    if (!vals)
        return (0);
    copy_vals(a, vals);
    cur = a;
    while (cur)
    {
        cur->val = compute_rank(cur->val, vals, n);
        cur = cur->next;
    }
    free(vals);
    return (1);
}

Pourquoi un tableau auxiliaire vals ?

Si on parcourait a et qu'on remplaçait directement les valeurs, on perdrait la valeur originale au fur et à mesure. Le compute_rank compte combien de nodes ont une valeur strictement inférieure → il a besoin des valeurs originales de tous les nodes, pas juste celle du courant.

Solution : on copie d'abord toutes les valeurs originales dans un tableau, puis on calcule les rangs en utilisant ce tableau comme référence figée.

Les helpers copy_vals et compute_rank

static void copy_vals(t_stack *a, int *vals)
{
    int     i;

    i = 0;
    while (a)
    {
        vals[i++] = a->val;
        a = a->next;
    }
}

static int compute_rank(int target, int *vals, int n)
{
    int     rank;
    int     i;

    rank = 0;
    i = 0;
    while (i < n)
    {
        if (vals[i] < target)
            rank++;
        i++;
    }
    return (rank);
}

copy_vals : parcours simple, copie chaque val dans le tableau.

compute_rank : compte combien de valeurs sont strictement inférieures à target. Si target est le plus petit, aucune n'est inférieure → rank = 0. Si target est le 2e plus petit, 1 valeur est inférieure → rank = 1. Etc.

★ Complexité O(n²) — pourquoi c'est OK
Pour chaque node (n), on parcourt le tableau entier (n) → O(n²). Pour 500 nums = 250 000 comparaisons. Quelques millisecondes. Largement assez rapide. On n'a pas besoin d'un algo de rank plus subtil (genre tri auxiliaire) pour cette taille.

9.5Phase 2 : push_to_b — pousser par chunks

void push_to_b(t_stack **a, t_stack **b)
{
    int     chunk_size;
    int     target;
    int     pushed;
    int     chunk_max;

    if (stack_size(*a) <= 100)
        chunk_size = 16;
    else
        chunk_size = 35;
    target = stack_size(*a);
    pushed = 0;
    while (pushed != target)
    {
        chunk_max = (pushed / chunk_size + 1) * chunk_size - 1;
        if ((*a)->val <= chunk_max)
        {
            pb(a, b);
            pushed++;
        }
        else
            ra(a);
    }
}

Le choix de chunk_size

  • Si pile ≤ 100 → chunks de 16 (≈ 6-7 chunks pour 100)
  • Sinon → chunks de 35 (≈ 14-15 chunks pour 500)

Pourquoi ces valeurs ? Empiriquement, ce sont des points d'équilibre entre "trop de chunks" (beaucoup de transitions, plus d'ops) et "pas assez" (B mal structurée, plus de coûts à phase 3). On a testé et tuned. Pour 100 %, on irait plus fin (genre sqrt(n) * constante).

La boucle principale

On boucle tant qu'il reste des éléments dans a (pushed != target, avec target = stack_size(*a) initial).

À chaque itération :

  1. Calculer chunk_max = le rang maximum accepté pour le chunk en cours
  2. Si (*a)->val <= chunk_max → l'élément appartient au chunk → pb + incrémenter pushed
  3. Sinon → ra, on saute, on s'en occupera dans un chunk plus tard

L'astuce : chunk_max est recalculé à chaque itération selon la valeur de pushed. Ça veut dire qu'au fur et à mesure qu'on pousse, on passe automatiquement aux chunks suivants. On verra la formule au §9.6.

⚠ Note : target = stack_size, pas stack_size - 3
Dans la version finale, on pousse tout sur b (target = n). On ne laisse PAS 3 éléments sur a pour sort_3. Pourquoi ? Voir §9.8 — le bug initial qu'on a corrigé.

9.6La formule chunk_max décortiquée

chunk_max = (pushed / chunk_size + 1) * chunk_size - 1;

C'est la formule clé. Décortiquons.

Étape par étape

Cas chunk_size = 16. Voyons ce que ça donne pour différentes valeurs de pushed :

pushedpushed/16+1*16-1chunk_maxChunk actuel
001161515Chunk 0 (rangs 0-15)
501161515Chunk 0
1501161515Chunk 0
1612323131Chunk 1 (rangs 16-31)
2012323131Chunk 1
3223484747Chunk 2 (rangs 32-47)

L'interprétation

  • pushed / chunk_size = numéro du chunk en cours (division entière)
  • (pushed / chunk_size + 1) * chunk_size = première valeur du chunk suivant
  • ... - 1 = dernière valeur du chunk en cours

Pourquoi cette formule plutôt qu'une variable explicite

Alternative naïve :

int chunk_num = 0;
int chunk_max = chunk_size - 1;
int in_chunk = 0;

while (pushed != target)
{
    if ((*a)->val <= chunk_max)
    {
        pb(a, b);
        pushed++;
        in_chunk++;
        if (in_chunk == chunk_size)
        {
            chunk_num++;
            chunk_max += chunk_size;
            in_chunk = 0;
        }
    }
    else
        ra(a);
}

Fonctionne mais nécessite 3 variables additionnelles. La formule chunk_max = (pushed / chunk_size + 1) * chunk_size - 1 dérive tout de pushed, plus compact.

9.7Phase 3 : push_back_to_a — ramener par max

void push_back_to_a(t_stack **a, t_stack **b)
{
    while (*b)
    {
        rotate_max_to_top(b);
        pa(a, b);
    }
}

L'algorithme

  1. Tant que b n'est pas vide :
    • Trouver le max de b
    • L'amener au top via rb ou rrb (le chemin le plus court)
    • Faire pa pour le déplacer au top de a

Pourquoi on ramène le max d'abord

Parce qu'on veut que a finisse trié croissant (petit en top). On commence par mettre le plus grand au top de a, puis on met des plus petits par-dessus. À la fin, le plus petit est en top, le plus grand au bottom. ✓

Comment trouver et amener le max

Symétrique de find_min_pos / rotate_min_to_top du Ch. 08 :

static int find_max_pos(t_stack *b)
{
    int     pos;
    int     max_pos;
    int     max_val;

    pos = 0;
    max_pos = 0;
    max_val = b->val;
    while (b)
    {
        if (b->val > max_val)
        {
            max_val = b->val;
            max_pos = pos;
        }
        b = b->next;
        pos++;
    }
    return (max_pos);
}

static void rotate_max_to_top(t_stack **b)
{
    int     size;
    int     pos;

    size = stack_size(*b);
    pos = find_max_pos(*b);
    if (pos <= size / 2)
        while (pos-- > 0)
            rb(b);
    else
        while (pos++ < size)
            rrb(b);
}

Même logique que rotate_min_to_top mais sur b et pour le max au lieu du min. Choix optimal entre rb et rrb selon la position.

9.8Le piège à éviter : pourquoi target = n (et pas n − 3)

En lisant le code de sort_5 (Ch 8), tu vas avoir une tentation : "tiens, dans sort_5 on laisse 3 éléments sur a pour faire un sort_3 final — pourquoi pas faire pareil dans Turk ?". C'est une tentation légitime, mais elle casse l'algorithme. Voilà pourquoi.

⚠ La tentation à éviter
Tu pourrais écrire : 
target = stack_size(*a) - 3;     // laisse 3 sur a

// puis dans sort_big :
index_stack(*a);
push_to_b(a, b);
sort_3(a);                       // trier les 3 restants
push_back_to_a(a, b);
Logique : "ça réutilise sort_3, économise quelques ops". Mais c'est faux.

Pourquoi ça ne marche pas

Tout repose sur un invariant que push_back_to_a a besoin de respecter pour produire une pile triée :

★ L'invariant clé de push_back_to_a
Toutes les valeurs sur b doivent rester < toutes les valeurs restant sur a.

Sinon, quand on ramène le max de b sur a (via pa), ce max peut être plus petit que ce qui est déjà sur a → l'ordre croissant casse.

Avec target = n − 3, tu laisses 3 éléments arbitraires sur a (les 3 derniers que la boucle n'a pas eu le temps de pousser). Ces 3 éléments n'ont aucune raison d'être les 3 plus grands — ce sont simplement ceux qui étaient en haut de a au moment où pushed a atteint target.

Exemple concret du piège

Reprends l'exemple du walkthrough §9.3b. Avec target = 8 − 3 = 5 au lieu de 8 :

a indexée = [4, 1, 7, 2, 0, 5, 3, 6]

// On pousse jusqu'à pushed == 5 (rangs 0, 1, 2 du chunk 0 + 3, 4 du chunk 1)
// Résultat possible :
a = [7, 5, 6]    b = [3, 4, 0, 2, 1]

// Or attends : 5 reste sur a, mais 4 et 3 sont sur b !
// L'invariant "valeurs sur b < valeurs sur a" est CASSÉ.

// sort_3(a) trie a : [5, 6, 7] (OK)
// push_back_to_a ramène le max de b... mais le max de b = 4
// pa met 4 EN HAUT de a → a = [4, 5, 6, 7]
// Puis 3 → [3, 4, 5, 6, 7]
// ...
// Au final, a sera bien trié dans CE cas, mais dans d'autres cas où b finit
// avec un max > min de a, l'ordre se casse irrémédiablement.

En pratique, sur ~5-10 % des piles aléatoires, l'invariant casse et tu obtiens un "KO" du checker. C'est le piège classique de cette approche.

La solution propre : pousser tout

Pour garantir que l'invariant tient, on pousse tous les éléments sur b. Comme ça, à la fin de la phase 2 :

  • a est vide (donc "valeurs sur b < valeurs sur a" est trivialement vrai — aucune valeur sur a)
  • push_back_to_a ramène en sélectionnant le max → ordre croissant garanti
// Version correcte
target = stack_size(*a);          // pousser tout

// Dans sort_big :
index_stack(*a);
push_to_b(a, b);
push_back_to_a(a, b);          // pas de sort_3 nécessaire

Coût : 3 ops supplémentaires (on pousse 3 éléments qu'on aurait pu garder), mais algorithme correct dans 100 % des cas. Le trade-off est ridicule : 3 ops contre la garantie de fonctionner.

★ Leçon générale
Les "optimisations élégantes" peuvent casser des invariants subtils. Code d'abord la version simple et correcte, vérifie qu'elle marche sur des centaines de cas tests, puis optimise seulement si tu en as besoin.

Pour aller à 100 % : tu pourrais réintroduire un sort_3 final, mais en t'assurant que les 3 nodes laissés sur a sont EXACTEMENT les 3 plus grands (par exemple en arrêtant la phase 2 quand chunk_max atteint n − 4, ce qui garantit que les rangs n−3, n−2, n−1 restent sur a).

9.9L'orchestrateur sort_big

void sort_big(t_stack **a, t_stack **b)
{
    index_stack(*a);
    push_to_b(a, b);
    push_back_to_a(a, b);
}

Trois lignes. Chaque ligne déclenche une phase de l'algo Turk.

Note : on ne check pas si index_stack rate

index_stack retourne 0 si malloc rate. Dans notre code, on ignore ce retour pour rester simple. Si on voulait être 100 % défensif, on pourrait :

if (!index_stack(*a))
{
    write(2, "Error\n", 6);
    return ;
}

Mais avec valgrind clean sur des centaines de cas testés, on accepte le risque (très faible) d'un malloc qui rate.

9.11Récap du chapitre

★ L'algo Turk en 3 phases
  1. index_stack : remplacer chaque valeur par son rang (0 à n-1) pour avoir des chunks bien définis.
  2. push_to_b : pousser tous les éléments sur b par chunks, en utilisant la formule chunk_max = (pushed/size + 1) * size - 1.
  3. push_back_to_a : ramener les éléments en sélectionnant le max de b à chaque itération (avec optim rb/rrb).
★ Pourquoi ça marche
  • Phase 1 normalise les valeurs en [0, n-1] → chunks bien dimensionnés.
  • Phase 2 distribue les éléments par plages de valeurs sur b, créant une structure approximativement triée (décroissante).
  • Phase 3 exploite cette structure pour ramener efficacement (max au top de b souvent ≈ déjà bien placé).
  • Coût total ~3-5n ops pour n éléments.
Auto-éval
Pourquoi on indexe avant de pousser ?
Pour que les valeurs soient dans [0, n-1], ce qui permet de définir des chunks bien dimensionnés (par ex. chunk 0 = rangs 0-15). Sans indexation, on ne saurait pas où placer les frontières de chunks par rapport à des valeurs arbitraires.
Que vaut chunk_max quand pushed = 0 et chunk_size = 16 ?
chunk_max = (0/16 + 1) * 16 - 1 = 1 * 16 - 1 = 15. Donc on accepte les rangs 0 à 15 (le chunk 0).
Si tu pousses un élément hors du chunk en cours, qu'est-ce qui se passe ?
Tu fais ra(a) au lieu de pb. L'élément passe en bas de a (rotation). Il sera évalué à nouveau au tour suivant. Une fois que tu passes au chunk suivant (par incrémentation de pushed), chunk_max augmente et l'élément finit par être accepté.
Pourquoi push_back_to_a ramène le max et pas le min ?
Parce qu'on construit a en empilant au top. Si on ramène le max en premier, il finit au bottom de a (les autres viennent par-dessus). Le min finit donc au top à la fin. → Pile triée croissant comme demandé.

PARTIE IV · CHAPITRE 08

Tris pour petites piles

sort_3 hardcodé, sort_5 délègue à sort_3

8.1Vue d'ensemble

Pour les piles de taille ≤ 5, on n'utilise pas l'algo Turk (qui serait disproportionné). On a des algos dédiés, optimisés cas par cas :

TailleMéthodeOps max
0 ou 1Rien, c'est déjà trié0
2Test simple + sa éventuel1
3sort_3 hardcodé sur les 6 permutations2
4-5sort_5 : push 1-2 plus petits sur b, sort_3 sur a, pa pa~10
> 5Algo Turk (Ch. 09)~700 pour 100, ~7500 pour 500

Pourquoi des algos dédiés pour les petites tailles ?

  • Pour 3 nums, 2 ops max sont suffisantes en hardcodant. Turk ferait 5-10 ops.
  • Pour 5 nums, ~10 ops via délégation à sort_3. Turk en ferait ~25.
  • L'algo Turk a un overhead (indexation, chunks) qui n'est rentable que pour les grosses piles.

De plus, sort_5 est réutilisé par sort_big indirectement : Turk laisse 3 éléments sur a à la fin, qu'on aurait pu trier avec sort_3. Mais dans notre implémentation finale, on push tout sur b (voir Ch. 09), donc sort_3 n'est utilisé que pour les piles directement de taille 3.

8.2is_sorted — vérifier avant de trier

int is_sorted(t_stack *stack)
{
    while (stack && stack->next)
    {
        if (stack->val > stack->next->val)
            return (0);
        stack = stack->next;
    }
    return (1);
}

L'algorithme

On parcourt la chaîne et on vérifie que chaque node a une valeur ≤ son suivant. Si jamais on trouve val > next->val, ce n'est pas trié → return 0. Sinon, on est arrivé au bout sans trouver d'incohérence → return 1.

Conditions de boucle

while (stack && stack->next) :

  • stack : on n'est pas tombé sur NULL
  • stack->next : il y a au moins un node après (sinon on ne peut pas comparer)

Pourquoi cet appel dans main

if (!is_sorted(a))
    sort(&a, &b);

Optimisation : si la pile arrive déjà triée, on évite tout le travail de tri. Pas une ligne d'op sur stdout, exit propre.

Sans cette ligne, sort(&a, &b) serait appelé même sur une pile triée. sort détecterait probablement et ferait rien (selon l'algo), mais ça coûterait des cycles inutiles. Le is_sorted est un short-circuit propre.

8.3Le dispatcher sort

void sort(t_stack **a, t_stack **b)
{
    int     size;

    size = stack_size(*a);
    if (size <= 1)
        return ;
    if (size == 2)
    {
        if ((*a)->val > (*a)->next->val)
            sa(a);
        return ;
    }
    if (size == 3)
        sort_3(a);
    else if (size <= 5)
        sort_5(a, b);
    else
        sort_big(a, b);
}

Le pattern dispatcher

Une seule fonction sort qui dispatche vers la bonne implémentation selon la taille. Avantages :

  • main appelle juste sort(&a, &b) sans se soucier de la taille
  • Si on veut changer la stratégie (par ex. sort_5 pour 4-7 au lieu de 4-5), on ne change qu'un endroit
  • Tests faciles : on peut tester chaque taille indépendamment

Les 4 branches

sizeBranchePourquoi
0 ou 1return ;déjà trié par définition
2Test direct + satrop simple pour mériter une fonction dédiée
3sort_3(a)6 permutations hardcodées
4 ou 5sort_5(a, b)délégation à sort_3
≥ 6sort_big(a, b)algorithme Turk

8.4sort_3 — 6 cas hardcodés

Le principe : énumérer toutes les permutations

Avec 3 éléments distincts (rappel : pas de doublons grâce au parser), il y a 3! = 6 permutations possibles. Pour chacune, on connaît la stratégie optimale.

On utilise les variables top, mid, bot pour représenter les 3 valeurs lues depuis la pile, et on teste leurs relations.

Le tableau des 6 cas

PileConditionOpsStratégie
[1, 2, 3]top < mid < bot0déjà trié, return
[2, 1, 3]top > mid && top < bot1sa → [1, 2, 3]
[3, 1, 2]top > mid && top > bot && mid < bot1ra → [1, 2, 3]
[2, 3, 1]top < mid && top > bot1rra → [1, 2, 3]
[1, 3, 2]top < mid && mid > bot && top < bot2rra + sa → [1, 2, 3]
[3, 2, 1]top > mid && mid > bot2sa + rra → [1, 2, 3]

Le code

void sort_3(t_stack **a)
{
    int     top;
    int     mid;
    int     bot;

    top = (*a)->val;
    mid = (*a)->next->val;
    bot = (*a)->next->next->val;
    if (top < mid && mid < bot)
        return ;
    else if (top > mid && top < bot)
        sa(a);
    else if (top > mid && top > bot && mid < bot)
        ra(a);
    else if (top < mid && top > bot)
        rra(a);
    else if (top < mid && mid > bot && top < bot)
    {
        rra(a);
        sa(a);
    }
    else if (top > mid && mid > bot)
    {
        sa(a);
        rra(a);
    }
}

Vérification d'un cas : [3, 1, 2]

Pile : top=3, mid=1, bot=2. Test des conditions :

  • top < mid ? 3 < 1 ? NON
  • top > mid && top < bot ? 3 > 1 ✓, 3 < 2 ? NON
  • top > mid && top > bot && mid < bot ? 3 > 1 ✓, 3 > 2 ✓, 1 < 2 ✓ → MATCH

Action : ra(a). Avant : [3, 1, 2], après ra : [1, 2, 3]. ✓ Trié en 1 op.

Pourquoi cette structure if/else if

Les conditions sont exhaustives et mutuellement exclusives : pour 3 valeurs distinctes, exactement une condition match. Le if/else if vérifie séquentiellement, court-circuite dès qu'une matche, et garantit qu'on ne fait aucune op si déjà trié.

★ Limite théorique : 2 ops max
Mathématiquement, pour trier 3 éléments avec les ops disponibles, le pire cas est 2 ops. Notre sort_3 l'atteint pour tous les cas. C'est optimal.

Erreur de débutant à éviter

Si tu te trompes dans l'une des conditions (par ex. tu oublies un &&), tu peux entrer dans la mauvaise branche et faire 2-3 ops alors qu'1 suffirait. Test ton sort_3 sur les 6 permutations possibles avant de passer à la suite.

8.5sort_5 — déléguer à sort_3

L'idée centrale

On a déjà sort_3 qui trie 3 éléments. Pour 5 éléments, on réduit le problème :

  1. Push les 2 plus petits de a vers b
  2. Il reste 3 éléments dans a → on appelle sort_3
  3. Ramène les 2 éléments de b via pa + pa

Pourquoi les plus petits sur b ? Parce qu'à la fin, on les ramène au top de a via pa. Comme on les a poussés dans l'ordre croissant (le plus petit en dernier), ils reviennent dans le bon ordre (le plus petit reste au top de a).

Walk-through complet sur [5, 4, 3, 2, 1]

État initial : a = [5, 4, 3, 2, 1] b = [] Étape 1 : amener 1 (min) au top → push sur b rra rra rra → a = [3, 2, 1, 5, 4]... attendons, faisons plutôt : on calcule la position du min via find_min_pos pos=4 → on choisit rra (plus court, 1 ops) → a = [1, 5, 4, 3, 2] pb → a = [5, 4, 3, 2], b = [1] Étape 2 : amener 2 (nouveau min) au top → push sur b find_min_pos(a) = 3 → rra (1 op) → a = [2, 5, 4, 3] pb → a = [5, 4, 3], b = [2, 1] Étape 3 : sort_3 sur [5, 4, 3] top=5, mid=4, bot=3 → top > mid > bot → sa puis rra sa → [4, 5, 3] rra → [3, 4, 5] Étape 4 : pa pa pour ramener b sur a pa → a = [2, 3, 4, 5], b = [1] pa → a = [1, 2, 3, 4, 5], b = [] Total ops : 9 (1 rra + 1 pb + 1 rra + 1 pb + 1 sa + 1 rra + 2 pa = 8 ops... note : variable selon le cas, max 12 ops)

👉 Animation détaillée : sort_5 step-by-step

Le code

void sort_5(t_stack **a, t_stack **b)
{
    int     to_push;

    to_push = stack_size(*a) - 3;
    while (to_push-- > 0)
    {
        rotate_min_to_top(a);
        pb(a, b);
    }
    sort_3(a);
    while (*b)
        pa(a, b);
}

Décortiquage

  • to_push = stack_size(*a) - 3; : combien d'éléments doivent partir sur b ? Si a a 5, c'est 2. Si a a 4, c'est 1.
  • while (to_push-- > 0) : on répète to_push fois.
  • rotate_min_to_top(a); pb(a, b); : amène le min au top, push sur b.
  • sort_3(a); : trie les 3 restants.
  • while (*b) pa(a, b); : tant que b n'est pas vide, ramène un élément sur a.

Le code est court parce qu'il compose des briques existantes : rotate_min_to_top, pb, sort_3, pa. Chaque brique fait UNE chose.

8.6find_min_pos — trouver la position du min

int find_min_pos(t_stack *a)
{
    int     pos;
    int     min_pos;
    int     min_val;

    pos = 0;
    min_pos = 0;
    min_val = a->val;
    while (a)
    {
        if (a->val < min_val)
        {
            min_val = a->val;
            min_pos = pos;
        }
        a = a->next;
        pos++;
    }
    return (min_pos);
}

L'algorithme classique du "trouve le min"

  1. Init : on suppose que le 1er élément est le min (position 0, valeur a->val).
  2. Parcours : pour chaque élément, si sa valeur est plus petite que min_val, on met à jour min_val et min_pos.
  3. Retour : la position du min trouvée.

O(n) — un seul parcours.

Pourquoi on retourne la position et pas le min ?

Parce que pour amener le min au top, on a besoin de savoir combien de rotations il faut. La valeur du min en elle-même ne nous intéresse pas à ce moment. La position dit "il faut pos ra pour le ramener au top".

8.7rotate_min_to_top — choisir ra ou rra

void rotate_min_to_top(t_stack **a)
{
    int     size;
    int     pos;

    size = stack_size(*a);
    pos = find_min_pos(*a);
    if (pos <= size / 2)
    {
        while (pos-- > 0)
            ra(a);
    }
    else
    {
        while (pos++ < size)
            rra(a);
    }
}

L'optimisation : choisir le chemin le plus court

Si le min est à la position pos, on peut le ramener au top de 2 façons :

  • ra pos fois : le fait remonter par le haut (chaque ra fait avancer d'un cran)
  • rra (size - pos) fois : le fait remonter par le bas

On choisit la méthode la moins coûteuse.

Pile [3, 5, 1, 4, 2], size=5, min=1 à pos=2 Option A — ra : ra ra → 2 ops [3, 5, 1, 4, 2] → [5, 1, 4, 2, 3] → [1, 4, 2, 3, 5] Option B — rra : rra rra rra → 3 ops [3, 5, 1, 4, 2] → [2, 3, 5, 1, 4] → [4, 2, 3, 5, 1] → [1, 4, 2, 3, 5] Option A gagne (2 < 3).

Le critère pos <= size / 2

Si pos est dans la 1ère moitié (proche du top), c'est plus court via ra. Sinon, plus court via rra.

Exemple pour size=5 (size/2 = 2) :

  • pos = 0 → 0 ops
  • pos = 1 → 1 ra (vs 4 rra)
  • pos = 2 → 2 ra (vs 3 rra)
  • pos = 3 → 2 rra (vs 3 ra)
  • pos = 4 → 1 rra (vs 4 ra)

8.8Stratégie sort_5 — pourquoi ça marche

L'invariant

À l'étape "push 2 plus petits sur b", on s'assure que les valeurs de b sont toutes < les valeurs de a. Pourquoi ? Parce qu'on pousse spécifiquement les 2 plus petits.

Conséquence : quand on ramène avec pa, on met d'abord le 2e-plus-petit (en haut de b), puis le 1er-plus-petit (au bottom de b, désormais en haut). Ils arrivent au-dessus des 3 que sort_3 a déjà triés.

L'ordre final

Si b = [2, 1] (top=2, bottom=1) et a = [3, 4, 5] (top=3, trié), alors :

  • pa : a = [2, 3, 4, 5], b = [1]
  • pa : a = [1, 2, 3, 4, 5], b = []

La pile est triée. ✓

★ La condition cachée
Pour que ça marche, il faut absolument que les valeurs sur b soient toutes < toutes celles sur a. Si on pousse n'importe quoi sur b (pas spécifiquement les plus petits), à la fin pa mettrait des valeurs trop grandes en haut de a → pile pas triée.

C'est exactement le piège qu'on a découvert dans la phase Turk (Ch. 09) — la première version laissait 3 éléments arbitraires sur a, et l'invariant cassait.

8.9Récap du chapitre

★ Les algos par taille
  • is_sorted : court-circuit dans main si pile arrive triée.
  • Dispatcher sort : route vers la bonne implémentation.
  • sort_3 : 6 if/else if hardcodés, 2 ops max.
  • sort_5 : pousse les 2 plus petits sur b, sort_3 sur a, pa pa.
  • Helpers find_min_pos et rotate_min_to_top (avec optim ra/rra).
Auto-éval
Pourquoi hardcoder 6 cas pour sort_3 et pas un algo générique ?
Parce que pour 3 éléments distincts, il n'y a que 6 permutations. On peut toutes les énumérer et donner la solution optimale (2 ops max) à chacune. Un algo générique comme insertion sort ferait potentiellement plus d'ops. Hardcoder = optimal pour ce cas spécifique.
Dans sort_5, pourquoi on pousse les plus petits sur b et pas les plus grands ?
Parce qu'à la fin on les ramène via pa qui les met au top de a. On veut que les plus petits se retrouvent au top une fois la pile triée. Si on poussait les plus grands, ils reviendraient au top de a et casseraient l'ordre.
Pourquoi rotate_min_to_top choisit ra ou rra selon pos <= size/2 ?
Pour minimiser le nombre d'ops. Si le min est dans la 1ère moitié, ra (par le haut) est plus court. Sinon, rra (par le bas) est plus court. Le seuil size/2 définit le point d'inflexion.
Que retourne is_sorted sur une pile vide ?
1 (vrai). Une pile vide est considérée comme triée par convention. La boucle while (stack && stack->next) ne s'exécute pas, on tombe directement sur return (1).

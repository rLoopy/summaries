PARTIE I · CHAPITRE 02

Linked lists & t_stack

la structure de données de push_swap : pourquoi, comment, et les pièges

2.1Pourquoi pas un tableau ?

★ Mini-glossaire : la notation big-O
Tu vas voir O(1), O(n), O(n²) dans la suite. Définition rapide :
  • O(1) = travail constant, peu importe la taille des données. Ex: lire le 1er élément d'une liste.
  • O(n) = travail proportionnel à n (la taille). Ex: parcourir toute la liste.
  • O(n²) = travail = n × n. Ex: comparer chaque paire d'éléments. Ça grandit vite.
Plus c'est bas (O(1) < O(n) < O(n²)), plus l'algo est rapide pour de grandes tailles.

Pour stocker une pile de nombres, deux structures candidates :

Tableau (int *arr)

  • Accès direct à n'importe quel index : arr[5] instantané
  • Mémoire contigüe = cache-friendly
  • Taille fixée au malloc initial
  • Insérer au début = décaler tout le reste → O(n)
  • Push/pop au top = décaler tout → O(n)

Linked list (t_stack *)

  • Pas d'accès direct : pour aller au 5e, on doit parcourir
  • Mémoire dispersée
  • Taille dynamique : on alloue chaque node à la demande
  • Insérer/retirer au début = O(1) — juste reconnecter
  • Push/pop au top = O(1) ✓

Pour push_swap, les opérations critiques sont pa, pb, sa, sb qui touchent au top de la pile. La linked list excelle là-dessus (O(1) pour push/pop). C'est pour ça qu'on choisit cette structure.

★ Bonus pédagogique
Le tableau pourrait aussi marcher, mais alors :
  • tu devrais pré-allouer pour la taille max
  • chaque pa/pb coûte O(n) (décalage des éléments) → algo Turk consomme plus d'ops
Beaucoup d'étudiants utilisent un tableau quand même (souvent avec un index "top" qui flotte). C'est valide, mais moins élégant.

2.2Le concept de "node"

Un node (ou nœud) est une petite boîte en mémoire qui contient deux choses :

  1. Une donnée (pour nous : un int)
  2. Un pointeur vers le node suivant dans la chaîne
┌─────────────────┐ │ val : 42 │ ← la donnée │ next : 0x7FB0 │ ← l'adresse du node suivant └─────────────────┘

Le node ne sait pas qui est avant lui (chaîne simple), il sait juste qui est après. C'est ce qu'on appelle une singly linked list.

★ Doubly linked list ?
Il existe aussi des doubly linked lists où chaque node a prev et next. Plus pratique pour parcourir dans les 2 sens, mais plus de mémoire et plus de code. Pour push_swap, une simple chaîne suffit — la spec n'oblige pas, et tu ne fais que des opérations qui n'ont pas besoin de remonter.

2.3Chaîner les nodes

Plusieurs nodes ensemble forment une chaîne. Chacun pointe sur le suivant via son champ next :

chaîne de 4 nodes (valeurs 3, 1, 4, 2)
0x7FA0val=3
next=0x7FB0
→
0x7FB0val=1
next=0x7FC0
→
0x7FC0val=4
next=0x7FD0
→
0x7FD0val=2
next=?

Observations importantes :

  • Les adresses (0x7FA0, 0x7FB0...) ne sont pas forcément consécutives. J'ai aligné pour la lisibilité, mais en vrai elles peuvent être dispersées partout en RAM. Chaque malloc donne où il peut.
  • Ce qui relie les nodes, c'est uniquement le champ next. Si tu perds un next, tu perds tout ce qui suit.
  • Le dernier node a son next à ? pour l'instant — on va voir tout de suite ce qu'on met dedans.

2.4NULL = fin de chaîne

Convention universelle des linked lists : le dernier node a son champ next = NULL. C'est le marqueur de fin.

chaîne complète avec marqueur de fin
0x7FA0val=3
next=0x7FB0
→
0x7FB0val=1
next=0x7FC0
→
0x7FC0val=4
next=0x7FD0
→
0x7FD0val=2
next=NULL

Quand ton code parcourt la chaîne et arrive sur un node avec next == NULL, il sait que la chaîne est finie.

★ Pourquoi NULL ?
NULL est par convention l'adresse 0x0 (ou un équivalent). Aucun objet utilisateur ne vit jamais à cette adresse. Le système la réserve comme "adresse invalide". C'est parfait comme sentinelle parce qu'on est sûr qu'aucune adresse réelle ne sera confondue avec.

Le test if (!ptr) est équivalent à if (ptr == NULL).

2.5Le head — l'entrée de la chaîne

Pour pouvoir accéder à la chaîne depuis l'extérieur, tu as besoin d'une variable qui pointe sur le premier node. C'est le head.

le head pointe sur la 1ère boîte
0x100 0x7FA0
← variable head (sur la stack)

↓ pointe vers

0x7FA0val=3
next=0x7FB0
→
0x7FB0val=1
next=NULL

Quelques précisions importantes :

  • Le head est une variable séparée de la chaîne. Souvent une variable locale sur la stack, qui contient l'adresse du premier node sur le heap.
  • Si head == NULL, c'est que la pile est vide.
  • Dans push_swap, on a 2 piles → 2 variables head : stack_a et stack_b.
⚠ Perdre le head = catastrophe
Si tu écrases la variable head sans avoir sauvegardé son ancienne valeur, tu perds tous les nodes en aval. Ils sont toujours en RAM, mais tu n'as plus aucun moyen d'y accéder.
→ Memory leak permanent. valgrind te le signalera : "X bytes lost in N blocks".

2.6La struct t_stack

Maintenant en C, voilà comment on définit cette structure de node :

typedef struct s_stack
{
    int              val;
    struct s_stack  *next;
}   t_stack;

Décortiquons :

  • typedef struct s_stack {...} t_stack; = "définis un type t_stack qui est un alias pour struct s_stack". Sans ce typedef, tu devrais écrire struct s_stack *node; partout, ce qui est lourd.
  • Champ int val : la valeur stockée (4 octets).
  • Champ struct s_stack *next : un pointeur vers un autre node du même type. Note le struct s_stack dans la définition de next — c'est obligatoire parce que à ce moment-là, t_stack n'existe pas encore (le typedef n'est pas terminé).
★ Convention de nommage 42
Tu remarques le préfixe s_ pour la struct et t_ pour le typedef. C'est la convention 42 imposée par la norm :
  • s_xxx : nom de la struct elle-même (struct)
  • t_xxx : nom du typedef qui sert d'alias (type)
  • e_xxx : nom d'un enum (enum)
  • u_xxx : nom d'une union (union)
Si tu n'utilises pas ces préfixes, norminette te flag. C'est une question en peer-eval typique : "pourquoi s_stack et t_stack ?"

Taille en mémoire

offset 0 : int val (4 octets) offset 4 : padding (4 octets — pour aligner next sur 8) offset 8 : *next (8 octets sur 64-bit Linux) ───────────────────── sizeof(t_stack) = 16 octets
★ Padding ? Pourquoi pas 12 ?
Sur 64-bit Linux, un pointeur fait 8 octets et doit être aligné sur une adresse multiple de 8 (= contrainte hardware). Si on mettait next à l'offset 4 juste après val, il serait mal aligné. Le compilateur ajoute donc 4 octets de padding entre val et next pour respecter l'alignement. Résultat : 4 + 4 + 8 = sizeof(t_stack) = 16 et pas 12.

2.7. vs ->

Pour accéder à un champ d'une struct, deux syntaxes selon que tu as la struct elle-même ou un pointeur :

Tu as...Pour lire valPour modifier next
t_stack box; (la struct directe)box.valbox.next = ...
t_stack *node; (un pointeur vers struct)node->valnode->next = ...
t_stack box;             // struct directe sur la stack
box.val = 42;             // point pour la struct directe

t_stack *p = &box;        // p est un pointeur vers box
p->val = 42;              // flèche pour le pointeur

// les deux sont équivalents :
p->val
(*p).val             // déréf + point — personne n'écrit comme ça
★ Mnémo
La flèche -> fait deux choses d'un coup :
  1. déréférence le pointeur (suit l'adresse jusqu'à la struct)
  2. accède au champ
En push_swap, comme on travaille presque uniquement avec des t_stack *, tu vas toujours utiliser ->.

Chaîner les ->

Tu peux enchaîner les flèches :

node->next            // le node suivant
node->next->val       // la valeur du 2e node
node->next->next      // le 3e node
node->next->next->val // la valeur du 3e node

Chaque -> avance d'un cran dans la chaîne et récupère un champ.

Le piège du t_stack **

Quand tu as t_stack **stack, tu dois d'abord déréférencer pour atteindre le node, puis utiliser ->. Avec les bonnes parenthèses :

(*stack)->val      // ✓ déréf stack, puis ->val
*stack->val        // ✗ interprété comme *(stack->val), erreur

La priorité du C : -> est plus prioritaire que *. Donc *stack->val = *(stack->val) = tentative d'accéder à val sur un t_stack **, qui n'a pas de champ val. Erreur de compilation.

⚠ Règle
Dès que tu as un **, mets toujours des parenthèses pour le déréférencement avant -> :
  • (*stack)->val ✓
  • (*stack)->next ✓
  • (*stack)->next->val ✓ (les autres flèches n'ont pas besoin de parenthèses)

2.8Parcourir une chaîne avec un curseur

Pour visiter chaque node d'une linked list, le pattern universel utilise un curseur : une variable qui pointe sur le node courant, qu'on fait avancer de node en node.

t_stack *cur = head;        // le curseur part du head
while (cur)                  // tant qu'on n'est pas tombé sur NULL
{
    printf("%d\n", cur->val);    // fais un truc avec le node courant
    cur = cur->next;          // avance d'un cran
}

Déroulement sur [3, 1, 4] :

étape 0 : cur = head pointe sur [3] on traite 3 cur = cur->next → cur pointe sur [1] étape 1 : cur pointe sur [1] on traite 1 cur = cur->next → cur pointe sur [4] étape 2 : cur pointe sur [4] on traite 4 cur = cur->next → cur = NULL étape 3 : cur = NULL → la condition while(cur) devient fausse → on sort

Variante : s'arrêter sur le dernier

Parfois tu veux t'arrêter sur le dernier node, pas après. Par exemple si tu veux y attacher un nouveau node à la fin. Dans ce cas, la condition de boucle change :

t_stack *cur = head;
while (cur->next)       // tant que le SUIVANT existe
    cur = cur->next;     // avance
// ici : cur est sur le dernier node (cur->next == NULL)
★ Différence cruciale
  • while (cur) → s'arrête quand cur est NULL (tu es passé après la fin).
  • while (cur->next) → s'arrête quand le suivant est NULL (tu es pile sur le dernier).
Le choix dépend de ce que tu veux faire à la fin de la boucle :
  • Compter / afficher → while (cur)
  • Attacher à la fin → while (cur->next)

2.9Modifier vs lire — le piège des champs

Une subtilité critique : variables locales vs champs de struct. Ils peuvent contenir la même adresse à un moment, mais ils évoluent indépendamment.

t_stack *cur = head;       // cur et head pointent sur le même node initialement
cur = cur->next;            // modifier cur ne touche PAS head

Exemple concret du piège

Disons qu'on a head → [3] → [1] → [4] → NULL et on fait :

t_stack *first = head;     // first pointe sur [3]
t_stack *cur   = head;     // cur aussi pointe sur [3]
cur = cur->next;            // cur pointe maintenant sur [1]
// first → [3], cur → [1]   ─ ils ont divergé !

Maintenant attention : first->next est-il égal à cur ?

Oui à cet instant : first->next = adresse de [1] = ce que vaut cur. Mais c'est une coïncidence, pas une équivalence permanente.

Si on continue :

cur = cur->next;     // cur pointe sur [4]
// first->next pointe TOUJOURS sur [1] — on ne l'a pas modifié
// cur pointe sur [4] — la variable cur a bougé, mais le champ next de [3] n'a pas changé
★ La distinction fondamentale
  • Variable locale (comme cur, first) : une boîte sur la stack qui contient une adresse. Tu peux la modifier sans affecter le monde extérieur.
  • Champ de struct (comme node->next) : un emplacement à l'intérieur d'un node sur le heap. Le modifier change la chaîne pour tous ceux qui accèdent à ce node.

2.10Le pattern 2 pointeurs (fixe + curseur)

Beaucoup d'algorithmes sur linked lists utilisent 2 pointeurs simultanément : un qui reste fixe quelque part, et un autre qui marche.

Pourquoi on en a besoin ?

Imagine que tu veux rotate la pile : déplacer le 1er node à la fin. Tu dois :

  1. Te souvenir du 1er node (pour pouvoir le déplacer après)
  2. Marcher jusqu'au dernier (pour pouvoir attacher le 1er derrière lui)

Avec un seul curseur, c'est impossible : dès que tu avances, tu perds la référence au 1er.

Solution : 2 pointeurs :

t_stack *first = *stack;          // pointeur FIXE sur le 1er node
t_stack *last  = *stack;          // pointeur CURSEUR qui va marcher

// On fait avancer last (pas first) jusqu'au dernier node
while (last->next)
    last = last->next;

// Maintenant : first → [3] (le 1er), last → [2] (le dernier)
// On peut faire les manipulations qui les utilisent tous les deux

C'est le pattern qu'on utilise dans rotate et reverse_rotate. On y revient en détail au Ch. 07.

★ Quand 1 seul pointeur suffit
Pour les algos qui ne reviennent jamais en arrière (compter, afficher, free), un seul curseur suffit. Le 2e pointeur n'est nécessaire que si tu dois manipuler 2 endroits de la chaîne simultanément.

2.11Memory leaks & dangling pointers

Memory leak

Une fuite mémoire se produit quand tu perds l'accès à de la mémoire mallocée sans la free. Elle reste allouée jusqu'à la fin du programme.

t_stack *a = stack_new(42);   // alloue sur le heap, adresse = 0x7FA0
a = NULL;                       // on perd l'adresse !
// La zone 0x7FA0 est toujours allouée mais inaccessible : leak

Dans une linked list, perdre le head = perdre TOUS les nodes :

t_stack *a = build_stack(values, 100);   // 100 nodes alloués
a = NULL;                                // 100 nodes lost

Dangling pointer

Un pointeur fantôme pointe sur de la mémoire déjà libérée. Lire/écrire dessus = comportement indéfini (crash, corruption, données aléatoires).

t_stack *node = stack_new(42);
free(node);                    // node pointe maintenant sur de la mémoire libérée
int v = node->val;             // DANGER : comportement indéfini

La bonne pratique : après chaque free, mettre le pointeur à NULL :

free(node);
node = NULL;                // maintenant tout test `if (node)` sait que c'est invalide

C'est exactement ce qu'on fait dans stack_free à la fin avec *stack = NULL — pour que la variable de l'appelant pointe sur du vide propre.

⚠ Double-free
Conséquence d'un dangling pointer : si tu appelles free deux fois sur le même pointeur, c'est un double-free. Crash quasi-immédiat. Mettre à NULL après free protège contre ça : free(NULL) est légal et ne fait rien.

2.12Récap du chapitre

★ Les 10 concepts à retenir
  1. Linked list = chaîne de nodes reliés par leur champ next.
  2. Le dernier node a next = NULL (marqueur de fin).
  3. Le head = pointeur sur le 1er node (ou NULL si pile vide).
  4. typedef struct s_stack { int val; struct s_stack *next; } t_stack;
  5. Accès aux champs : node->val via pointeur, (*stack)->val via double pointeur.
  6. Parcours classique : cur = head; while (cur) cur = cur->next;
  7. Variante "arrêt sur dernier" : while (cur->next).
  8. Pour les algos qui manipulent 2 endroits de la chaîne, utiliser 2 pointeurs (un fixe, un curseur).
  9. Memory leak : on perd l'accès à du heap sans free. Dangling pointer : on accède à du heap déjà freed.
  10. Après free, mettre le pointeur à NULL pour éviter double-free et accès invalides.
Auto-éval du chapitre
Quelle est la différence entre cur = cur->next et cur->next = ... ?
cur = cur->next modifie la variable locale cur pour qu'elle pointe ailleurs (avance d'un cran).
cur->next = ... modifie le champ next du node pointé par cur (change la chaîne).
Le premier modifie où on regarde, le second modifie ce qu'on regarde.
Si tu veux parcourir et compter les nodes, tu utilises while (cur) ou while (cur->next) ?
while (cur). Tu veux traiter chaque node, y compris le dernier. while (cur->next) s'arrêterait sur le dernier sans le compter.
Tu free un node mais tu oublies de mettre son ancien pointeur à NULL. Que peut-il se passer ?
Si plus tard tu lis node->val : comportement indéfini (souvent crash, parfois lecture de mémoire corrompue).
Si tu fais free(node) à nouveau : double-free, crash quasi-immédiat.
La protection : free(node); node = NULL;

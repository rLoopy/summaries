Objectif peer-eval : pour chaque ligne importante, tu dois dire ce qu'elle fait, pourquoi, et ce qui casse si on l'enlève.

Architecture en une phrase

argv → parse_args → build_stack(a) → sort(a,b) → affiche ops → free

Les 3 algos de tri

  • n≤2 un sa si besoin
  • n=3 sort_3 — 6 cas hardcodés
  • n≤5 sort_5 — pb les petits, sort_3, pa
  • n>5 sort_big — indexation + chunks vers b + max vers a (Turk simplifié)
Question classique : « C'est quoi la structure de données ? » → Liste chaînée t_stack : val + next. La tête de pile = premier nœud. Pas de tableau pour a/b.

includes/push_swap.h Le contrat

typedef struct s_stack { int val; struct s_stack *next; } t_stack;

val : soit la valeur brute (avant tri big), soit le rang 0..n-1 après index_stack.
next : vers l'élément en dessous (plus profond dans la pile).

« Pourquoi pas un tableau ? » Le sujet impose des ops sur une pile — insert au milieu serait O(n) anyway ; la liste chaînée colle au modèle push/pop en tête O(1).

main.c Point d'entrée

values = parse_args(argc, argv, &n); if (!values) return (print_error()); a = build_stack(values, n); free(values); b = NULL; if (!is_sorted(a)) sort(&a, &b); stack_free(&a); stack_free(&b);
  • argc < 2 → rien à faire, exit 0 (pas d'erreur)
  • values libéré juste après build_stack — la pile a copié les ints
  • b toujours NULL au départ
  • print_error → write(2, "Error\n", 6) sur stderr
« Que se passe-t-il si malloc échoue dans build_stack ? » stack_add_bottom peut échouer silencieusement si stack_new retourne NULL — à connaître ; en pratique rare. main teste !a après build.

parser.c Lire les arguments

tokenize

  • 1 seul argv (./push_swap "3 1 4 2") → ft_split(argv[1], ' ')
  • plusieurs argv → copie argv[1..] avec ft_strdup

parse_args enchaîne

tokenize → count_tokens → convert_tokens → has_duplicates
if (*n == 0) return NULL; // pas de nombres = erreur if (has_duplicates(values, *n)) { free(values); return NULL; }
« Pourquoi ft_atol et pas atoi ? » Contrôle du dépassement INT : is_number vérifie syntaxe + borne INT_MIN/INT_MAX avant cast.

validator.c Validation

is_valid_int : optionnel +/-, puis que des chiffres.
is_number : syntaxe OK + ft_atol dans [INT_MIN, INT_MAX].
has_duplicates : double boucle O(n²) — compare chaque paire (i,j).

« Complexité des doublons ? » O(n²) — acceptable car n ≤ quelques milliers max ; on pourrait trier puis scanner en O(n log n) mais pas nécessaire ici.

stack.c La pile

Convention : *stack pointe sur le sommet (top). Le premier argv devient le top via build_stack qui ajoute en bas avec stack_add_bottom.

Ex. ./push_swap 3 1 4 → pile a vue du top : 3 → 1 → 4 → NULL

// stack_free : sauve next AVANT free next = cur->next; free(cur); cur = next;
« Pourquoi stack_add_bottom et pas push en tête ? » Pour respecter l'ordre des arguments : argv[1] doit être en haut de a.

op_swap.c sa / sb / ss

swap_top échange les valeurs des 2 premiers nœuds (pas les pointeurs).

tmp = (*stack)->val; (*stack)->val = (*stack)->next->val; (*stack)->next->val = tmp; write(1, "sa\n", 3);
« Pourquoi échanger val et pas les nœuds ? » Plus simple : les liens next restent identiques, seuls les contenus permutent. Même effet visuel sur la pile.

op_push.c pa / pb

top = *src; *src = top->next; // dépile src top->next = *dst; // ancien top dst devient 2e *dst = top; // top devient le nœud déplacé

pb = push_top(b, a) — prend le top de a, le met sur b.
pa = l'inverse.

« pb déplace le nœud ou copie ? » Déplace le nœud alloué — pas de nouveau malloc. Un seul maillon change de pile.

op_rotate.c ra / rb

Le premier devient le dernier : décroche la tête, parcourt jusqu'au dernier, recolle.

« Complexité de ra ? » O(n) — parcours jusqu'à la queue. Acceptable car n petit ou utilisé avec parcimonie dans l'algo.

op_reverse.c rra / rrb

Arrête à l'avant-dernier : while (cur->next->next) — le dernier nœud devient la nouvelle tête.

« Différence ra vs rra ? » ra : top → bottom. rra : bottom → top. Utilisés dans sort_3 et pour amener min/max en tête.

sort.c Dispatcher

size = stack_size(*a); if (size <= 1) return; if (size == 2) { if ((*a)->val > (*a)->next->val) sa(a); return; } if (size == 3) sort_3(a); else if (size <= 5) sort_5(a, b); else sort_big(a, b);

is_sorted : parcourt et vérifie stack->val <= stack->next->val (croissant du top vers le bas).

sort_3.c Trois entiers

Lit top, mid, bot — compare les 3 valeurs — au plus 2 ops selon la permutation.

Déjà trié top<mid<bot → rien
Ex. top>mid, top<bot → sa
Ex. top>mid>bot → sa puis rra
Ex. mid>bot, top<bot → rra puis sa
« Pourquoi pas un tri générique ? » 3! = 6 cas — table hardcodée = minimum d'ops garanti et code court.

sort_5.c Quatre ou cinq entiers

  1. to_push = size - 3 — on garde 3 dans a
  2. rotate_min_to_top puis pb (répété)
  3. sort_3(a) sur les 3 restants
  4. while (*b) pa — les petits reviennent dans le bon ordre car pb a empilé du plus grand au plus petit en top de b
// rotate_min_to_top : chemin court if (pos <= size / 2) while (pos--) ra(a); else while (pos++ < size) rra(a);
« Pourquoi ra si pos ≤ size/2 ? » Sur une pile circulaire, amener un élément en tête : soit on rotate vers le haut (ra), soit vers le bas (rra) — on prend le chemin le plus court.

index_stack.c Normalisation (rangs)

Remplace chaque valeur par son rang : nombre de valeurs strictement plus petites.

Ex. [42, 7, 99, 13, 5] → [3, 1, 4, 2, 0]

cur->val = compute_rank(cur->val, vals, n);

Après ça, trier par valeur = trier par ordre croissant des rangs 0..n-1.

« Pourquoi indexer ? » L'algo Turk travaille sur des positions relatives (chunks de rangs), pas sur des ints arbitraires — simplifie les seuils (chunk 0-15, 16-31…).

push_to_b.c Phase 2 — vider a vers b

Chunk size : 16 si n≤100, sinon 35.

chunk_max = (pushed / chunk_size + 1) * chunk_size - 1; if ((*a)->val <= chunk_max) { pb(a,b); pushed++; } else ra(a);

Boucle jusqu'à pushed == target (target = taille initiale de a). Chaque élément finit par être pb — les ra font tourner ceux pas encore dans le chunk courant.

« Que reste sur a à la fin ? » Rien — tout est sur b. Ensuite push_back_to_a reconstruit a trié.

push_back_to_a.c Phase 3 — reconstruire a

Tant que b non vide : amener le maximum de b en tête (rotate_max_to_top = rb ou rrb), puis pa.

Résultat : a reçoit les éléments du plus grand au plus petit → ordre croissant final.

« Pourquoi toujours le max ? » Comme sort_5 en sens inverse : empiler le plus grand d'abord sous les plus petits déjà placés = tri croissant en a.

sort_big.c Turk en 3 lignes

if (!index_stack(*a)) return; push_to_b(a, b); push_back_to_a(a, b);

Si index_stack échoue (malloc), on sort sans tri — cas limite à mentionner.

index → chunk push vers b → max pa vers a

libft/ Utilitaires

push_swap utilise surtout : ft_split, ft_strdup, ft_isdigit, malloc/free via libft.a linkée au link.

« C'est quoi libft.a ? » Archive statique compilée par le Makefile de libft — le linker résout les symboles au build.

Makefile Build

14 fichiers .c dans src/, flags -Wall -Wextra -Werror, objects dans obj/, link -lft.

Pas de bonus checker dans ce binaire — seulement les instructions sur stdout.

Exemple mental : 500 nombres

  1. Parse → 500 ints uniques dans a
  2. sort_big : valeurs → rangs 0..499
  3. push_to_b : chunks de 35, ~7250 ops typiques
  4. push_back_to_a : 499 fois (trouver max + pa)
  5. a trié, b vide
« Comment tu testes ? » ./push_swap $ARG | ./checker_OS $ARG ou checker_linux — le checker rejoue les ops et dit OK/KO.

Questions peer-eval (1/4)

Pourquoi t_stack ** et pas t_stack * ? Pour modifier le pointeur tête dans la fonction (push/pop changent la tête).
Où sont écrites les instructions ? Chaque op fait un write(1, "xx\n", len) — stdout, une op par ligne.
Que fait le programme si doublon ? parse_args retourne NULL → "Error\n" sur stderr, exit 1.
ss et rr existent ? Oui dans le .h et implémentés — utiles si tu étends, le tri actuel n'en a pas toujours besoin.

Questions peer-eval (2/4)

Comment tu sais que c'est trié avant sort ? is_sorted parcourt une fois — évite d'imprimer des ops inutiles.
Fuite mémoire ? values free après build_stack ; stack_free a et b ; tokens free dans parse_args.
Pourquoi pas qsort sur un tableau ? Le sujet impose le modèle 2 piles + 11 ops — le tri doit produire une séquence d'ops, pas juste ordonner des ints.

Questions peer-eval (3/4)

Explique pb sur [3,1,4] après index [2,0,1] — montre sur papier : top a, chunk_max, ra vs pb.
Pire cas sort_3 ? 2 ops (ex. sa + rra).
Bonus : pourquoi chunk 16 vs 35 ? Empirique / Turk — 16 pour petites piles, 35 pour réduire le nombre de rotations sur 500.

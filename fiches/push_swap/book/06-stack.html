stack.c — la pile chaînée

5 fonctions pour créer, modifier, mesurer, libérer la struct t_stack

6.1Vue d'ensemble

stack.c contient les 5 fonctions de base sur la struct t_stack. C'est la couche bas-niveau : tout le reste du projet s'appuie dessus.

FonctionJobSignature
stack_newfabriquer 1 nodet_stack *stack_new(int val)
stack_add_bottomajouter 1 node à la finvoid stack_add_bottom(t_stack **stack, int val)
stack_sizecompter les nodesint stack_size(t_stack *stack)
stack_freelibérer toute la pilevoid stack_free(t_stack **stack)
build_stackint[] → linked listt_stack *build_stack(int *values, int n)
★ Pourquoi exactement ces 5 fonctions
Le sujet impose 5 max par fichier. On a choisi ces 5 parce qu'elles couvrent tout le cycle de vie d'une pile : création (new), construction (add_bottom, build_stack), mesure (size), destruction (free). Les opérations de tri (sa, pb, ra...) vivent dans les fichiers op_*.c, pas ici.

6.2stack_new — fabriquer 1 node

t_stack *stack_new(int val)
{
    t_stack *node;

    node = malloc(sizeof(*node));
    if (!node)
        return (NULL);
    node->val = val;
    node->next = NULL;
    return (node);
}

Décortiquage ligne par ligne

Ligne 3 : t_stack *node;

Déclaration d'un pointeur local. À ce stade, node contient des octets aléatoires (variable non-initialisée). On va le remplir tout de suite.

Ligne 5 : node = malloc(sizeof(*node));

On demande au système 16 octets sur le heap (= sizeof(t_stack)). malloc retourne l'adresse de cette nouvelle zone, qu'on stocke dans node.

★ sizeof(*node) vs sizeof(t_stack)
Les deux donnent 16, mais sizeof(*node) est plus robuste : si tu changes le type de node plus tard, le sizeof s'adapte automatiquement. C'est une convention défensive.

Lignes 6-7 : if (!node) return (NULL);

Si malloc a échoué (RAM saturée), il retourne NULL. On propage l'erreur en retournant NULL aussi. Sans cette ligne, la ligne suivante crasherait (déréférencement de NULL).

Lignes 8-9 : node->val = val; node->next = NULL;

On remplit les 2 champs du node. val reçoit la valeur passée. next = NULL parce qu'un node fraîchement créé n'a pas encore de suivant.

Ligne 10 : return (node);

On retourne l'adresse du node, prêt à être utilisé.

État mémoire après stack_new(42)

stack (caller) heap ┌────────────┐ ┌──────────────────────┐ │ p = 0x7FA0 │ ──────► │ 0x7FA0: val=42 │ └────────────┘ │ next=NULL │ └──────────────────────┘

Test mental

t_stack *a = stack_new(42);
// a est un t_stack *, pointe sur un node {val=42, next=NULL}
// a est la "head" d'une linked list à 1 seul node

6.3stack_add_bottom — ajouter à la fin

void stack_add_bottom(t_stack **stack, int val)
{
    t_stack *new;
    t_stack *cur;

    new = stack_new(val);
    if (!new)
        return ;
    if (*stack == NULL)
    {
        *stack = new;
        return ;
    }
    cur = *stack;
    while (cur->next)
        cur = cur->next;
    cur->next = new;
}

Décortiquage par étapes

Étape 1 : fabriquer le node à ajouter (new = stack_new(val);). Si malloc rate, on sort en silence.

Étape 2 : cas particulier de la pile vide.

if (*stack == NULL)
{
    *stack = new;       // new devient le head
    return ;
}

Si *stack est NULL (= pile vide), notre new node devient le head. On modifie la variable de l'appelant via *stack = new (d'où le besoin du **). Puis on sort.

Étape 3 : cas pile non-vide. On parcourt jusqu'au dernier node.

cur = *stack;
while (cur->next)
    cur = cur->next;
// après la boucle : cur est sur le dernier node (cur->next == NULL)

Étape 4 : attacher new au dernier.

cur->next = new;

Pourquoi while (cur->next) et pas while (cur) ?

On veut s'arrêter sur le dernier (pour pouvoir lui attacher quelque chose), pas après. while (cur) ferait passer cur sur NULL, on aurait perdu la référence au dernier. while (cur->next) garantit qu'à la sortie, cur est pile sur le dernier (celui dont next == NULL).

Schéma d'exécution sur [3, 1] + add 5

Avant : *stack ─► [3] ─► [1] ─► NULL Étape 1 : new = stack_new(5) new ─► [5] ─► NULL Étape 3 : cur démarre sur head cur ─► [3] ─► [1] ─► NULL while (cur->next) : cur->next = [1], pas NULL → cur = cur->next cur ─► [1] while (cur->next) : cur->next = NULL → exit cur reste sur [1] Étape 4 : cur->next = new [1]->next = [5] Final : *stack ─► [3] ─► [1] ─► [5] ─► NULL

6.4Pourquoi t_stack ** en paramètre ?

Question légitime : pourquoi stack_add_bottom(t_stack **stack, ...) et pas juste t_stack *stack ?

L'argument central : modifier le head depuis la fonction

Dans le cas pile vide, on doit faire en sorte que la variable head de l'appelant change. Sans **, on ne pourrait modifier qu'une copie locale qui mourrait à la fin de la fonction.

Recap du §1.13-1.14 du Ch01 :

Type du paramètrePermet de modifier...
t_stack *stackles nodes de la pile, pas la variable head de l'appelant
t_stack **stackla variable head de l'appelant (= remplacer le head)

Démonstration concrète

Imagine qu'on n'utilise pas ** :

void add_naif(t_stack *stack, int val)
{
    t_stack *new = stack_new(val);
    if (stack == NULL)
        stack = new;        // modifie la COPIE locale, pas l'appelant !
    // ...
}

/* Dans main : */
t_stack *a = NULL;
add_naif(a, 42);
// a vaut TOUJOURS NULL — on a perdu le node !

C'est exactement la raison pour laquelle on passe &a et que le paramètre est **.

★ Règle générale
Chaque fois qu'une fonction doit potentiellement remplacer le pointeur head d'une linked list, elle doit prendre un paramètre **.
Dans push_swap : stack_add_bottom, stack_free, sa, pb, ra, etc. — toutes les ops qui modifient potentiellement le head.

6.5stack_size — compter les nodes

int stack_size(t_stack *stack)
{
    int     count;

    count = 0;
    while (stack)
    {
        stack = stack->next;
        count++;
    }
    return (count);
}

Notes

  • Paramètre t_stack * (simple étoile) : on ne va pas modifier le head, juste lire.
  • while (stack) : on continue tant qu'on n'a pas atteint NULL.
  • On réutilise la variable stack elle-même comme curseur. Ça marche parce que c'est une copie locale.
  • stack = stack->next avance d'un cran (modifie la copie locale).
  • count++ incrémente le compteur.

Pourquoi on peut se permettre de modifier stack ici

C'est une copie locale du pointeur head. Modifier stack dans stack_size ne touche pas la variable de l'appelant. C'est juste un curseur réutilisé.

Tu pourrais aussi écrire avec un curseur séparé :

int stack_size(t_stack *stack)
{
    t_stack *cur = stack;
    int count = 0;

    while (cur)
    {
        cur = cur->next;
        count++;
    }
    return (count);
}

Les deux versions fonctionnent identiquement. La 1ère est plus compacte (1 variable au lieu de 2). Question de style.

Complexité

O(n) — on visite chaque node une fois. Sur 100-500 nums, c'est instantané.

★ Optim possible (qu'on ne fait pas)
On pourrait stocker la taille comme un champ de la struct (genre head->size) et la mettre à jour à chaque pb/pa. Accès O(1). Mais ça complique tout le code des opérations. On préfère la simplicité — stack_size est appelé peu souvent (seulement au démarrage des algos de tri), donc O(n) ne coûte rien dans la pratique.

6.6stack_free — libérer la pile entière

void stack_free(t_stack **stack)
{
    t_stack *cur;
    t_stack *next;

    cur = *stack;
    while (cur)
    {
        next = cur->next;
        free(cur);
        cur = next;
    }
    *stack = NULL;
}

Le piège : pourquoi 2 pointeurs ?

Question légitime : pourquoi on a besoin de cur ET next ? Pourquoi pas juste boucler avec cur ?

Réponse : parce qu'on doit free un node avant de pouvoir avancer. Mais si on free d'abord, on n'a plus accès à cur->next (mémoire libérée). Donc on doit sauvegarder next AVANT le free.

Code naïf incorrect

// ❌ NE FAIT PAS ÇA
while (cur)
{
    free(cur);
    cur = cur->next;     // CRASH : cur a été freed, on lit en zone libérée
}

Code correct avec sauvegarde

while (cur)
{
    next = cur->next;    // 1. sauvegarde l'adresse du suivant
    free(cur);            // 2. free le courant
    cur = next;          // 3. avance avec la sauvegarde
}

Le *stack = NULL final

Après la boucle, tous les nodes sont libérés. Mais *stack (= la variable de l'appelant) pointe toujours sur le 1er node libéré → c'est un dangling pointer.

Pour éviter ça, on met *stack = NULL. Comme ça :

  • L'appelant ne peut pas accidentellement déréférencer un pointeur invalide
  • Un éventuel double-free serait inoffensif (free(NULL) est légal)
  • L'appelant peut tester if (a) ou if (!a) pour savoir si la pile est encore valide

6.7build_stack — int[] → linked list

t_stack *build_stack(int *values, int n)
{
    t_stack *stack;
    int     i;

    stack = NULL;
    i = 0;
    while (i < n)
    {
        stack_add_bottom(&stack, values[i]);
        i++;
    }
    return (stack);
}

Le pattern

  1. Init stack = NULL (pile vide au départ)
  2. Pour chaque valeur du tableau, on l'ajoute en bas via stack_add_bottom
  3. On retourne le head construit

L'ordre dans la pile

On utilise stack_add_bottom et pas stack_add_top. Pourquoi ?

Le sujet impose que le 1er argument soit en top de la pile. Avec stack_add_top, on aurait l'ordre inversé (le 1er argument finit en bas). Avec stack_add_bottom, l'ordre des arguments est préservé :

// args : 3 1 4 1 5
// build_stack itère i=0..4

i=0: add_bottom(3) → stack = [3]
i=1: add_bottom(1) → stack = [3, 1]
i=2: add_bottom(4) → stack = [3, 1, 4]
i=3: add_bottom(1) → stack = [3, 1, 4, 1]
i=4: add_bottom(5) → stack = [3, 1, 4, 1, 5]

// Top = 3 (le 1er argument) ✓

Et l'argument &stack ?

stack_add_bottom a besoin de pouvoir modifier le head, donc on passe &stack (l'adresse de la variable locale stack). Au premier appel, stack vaut NULL → stack_add_bottom remplit le head.

★ Cohérence dans le projet
On utilise build_stack juste après parse_args dans main. Le flow est : argv → parse_args → int *values → build_stack → t_stack *a → on peut commencer à trier.
★ Petite remarque sur la complexité
build_stack appelle stack_add_bottom N fois. Chaque add_bottom parcourt la chaîne jusqu'à la fin, donc visite ~N/2 nodes en moyenne. Au total : O(N²) pour construire une pile de N éléments.

Pour 500 nums, c'est ~125 000 itérations, soit quelques ms. Largement assez rapide.

Optim possible (qu'on ne fait pas) : garder un cache du dernier node (un pointeur "tail") qui permettrait un add_bottom en O(1). Mais ça complique stack_free et toutes les ops qui modifient la chaîne. Pour 500 nums max, le gain ne vaut pas la complexité. Question typique en peer-eval : "comment tu accélérerais build_stack pour 1 million de nums ?" → réponse : cache du tail.

6.8Récap du chapitre

★ Les 5 fonctions et leur intention
  • stack_new(val) : malloc + init un node. Retourne NULL si malloc rate.
  • stack_add_bottom(**, val) : 2 cas (vide → modifie head, sinon → attache à la fin). ** nécessaire pour le cas vide.
  • stack_size(*) : compte O(n), simple parcours.
  • stack_free(**) : pattern save-next-then-free + final *stack = NULL contre dangling.
  • build_stack(values, n) : convertit int[] en linked list, préserve l'ordre.
★ Pourquoi ** vs *
  • ** si la fonction peut remplacer le head (cas pile vide pour add_bottom, cas final pour free)
  • * si la fonction lit seulement (size) ou retourne un pointeur (build_stack)
Auto-éval du chapitre
Pourquoi 2 pointeurs dans stack_free ?
Pour pouvoir sauvegarder cur->next AVANT de free cur. Si on free d'abord, cur->next est en mémoire libérée → comportement indéfini. Le pattern next = cur->next; free(cur); cur = next; protège contre ça.
Pourquoi stack_add_bottom prend ** et stack_size prend * ?
stack_add_bottom doit pouvoir remplacer le head (cas pile vide) → besoin de **.
stack_size ne modifie rien, juste lit → * suffit, copie locale du pointeur utilisée comme curseur.
Que fait *stack = NULL à la fin de stack_free ?
Évite le dangling pointer. Sans cette ligne, la variable head de l'appelant pointerait sur de la mémoire libérée. Avec cette ligne, l'appelant a un pointeur NULL propre, et peut tester if (a) en confiance.

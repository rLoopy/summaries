CHAPITRE 01

Le sujet et le projet

ce qu on doit livrer, les contraintes, l architecture choisie

§1.1 — Le but du projet

Minitalk c'est un projet 42 qui te demande de coder deux programmes qui se parlent. Le défi : ils doivent communiquer uniquement via des signaux UNIX, sans utiliser de fichiers, pipes, sockets, ou autre mécanisme classique d'IPC (inter-process communication).

★ En une phrase
Un client envoie une string à un server en encodant chaque caractère bit par bit via SIGUSR1 (= 0) et SIGUSR2 (= 1).

Tu auras donc 2 binaires à compiler :

  • ./server — se lance en premier, affiche son PID et attend des messages
  • ./client <PID> <message> — envoie un message au server identifié par PID

§1.2 — Les contraintes du PDF

Le sujet impose plusieurs règles strictes :

★ Règles du sujet
  • Communication via signaux UNIX uniquement
  • 2 signaux autorisés : SIGUSR1 et SIGUSR2
  • Server doit afficher son PID au lancement
  • Server doit gérer plusieurs clients en série (pas besoin de restart)
  • Affichage sans délai — 100 caractères en moins d'1 seconde
  • Pas de segfault, pas de leak, pas de comportement bizarre
  • Max 1 variable globale par programme (et justifiée)
  • Compilation avec -Wall -Wextra -Werror
  • Norminette OK (sinon = 0)

§1.3 — Les fonctions autorisées

Le PDF liste précisément quelles fonctions tu peux utiliser. Pas plus, pas moins :

write       // pour afficher (pas printf !)
ft_printf   // ou ton équivalent
signal      // API legacy, à éviter
sigemptyset // pour vider un set de signaux
sigaddset   // pour ajouter un signal au set
sigaction   // API moderne, à privilégier
kill        // pour ENVOYER un signal (mal nommé)
getpid      // pour récupérer son propre PID
malloc      // alloc dynamique
free        // libération
pause       // bloquer jusqu'à un signal
sleep       // attendre N secondes
usleep      // attendre N microsecondes
exit        // quitter le programme
★ À retenir
Pas de printf dans le code de prod (sauf si tu as ton ft_printf de libft). On utilise write pour tout afficher. Et on utilise sigaction plutôt que signal (plus fiable).

§1.4 — Notre architecture

On a choisi une structure minimale :

minitalk/
├── includes/
│   └── minitalk.h        // 4 includes système
├── src/
│   ├── server.c          // 3 fonctions, ~70 lignes
│   └── client.c          // 3 fonctions, ~60 lignes
├── Makefile
└── README.md

Pourquoi 2 fichiers .c seulement ? Le projet est petit (~130 lignes). Pas besoin de splitter en 10 fichiers comme push_swap. Un fichier par binaire, c'est clair et la norminette passe (5 fonctions max par fichier — on en a 3 chacun).

§1.5 — Mandatory vs Bonus

Le sujet sépare le travail en 2 parties :

MandatoryBonus
Communication client → server bit par bit. Affichage du message côté server. Server accuse réception de chaque message (renvoie un signal au client). Support Unicode (UTF-8 multi-bytes).
★ Notre choix
On a fait uniquement le mandatory. Pas d'ACK serveur, pas d'Unicode. On utilise usleep(700) côté client pour éviter la perte de signaux. C'est l'approche classique et c'est largement suffisant pour la note de base.

§1.6 — Récap

★ À retenir de ce chapitre
  • 2 binaires : ./server et ./client
  • Communication via SIGUSR1 (= bit 0) et SIGUSR2 (= bit 1)
  • Encodage bit par bit (8 bits par char)
  • Fonctions autorisées : 14 (mémorise-les)
  • Norminette obligatoire, -Wall -Wextra -Werror
  • Max 1 global par programme (on en a 0)
  • Architecture : 2 fichiers .c + 1 header + Makefile

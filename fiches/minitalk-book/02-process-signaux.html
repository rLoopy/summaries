CHAPITRE 02

Process et signaux UNIX

la theorie de base pour comprendre tout le reste

§2.1 — Qu est-ce qu un process ?

Un process c est un programme en cours d execution. Quand tu lances ./server, le système crée un process. Quand tu lances ./client dans un autre terminal, c est un autre process. Ils sont indépendants.

Linux donne un numéro unique à chaque process : le PID (Process ID). C est ce numéro qui identifie un process. Avec ps aux tu peux voir tous les process et leur PID.

★ Le PID
Un nombre entier (généralement 1-65535) qui identifie de manière unique un process en cours sur la machine. Quand le process se termine, son PID peut être réattribué à un futur process.

Dans notre code :

  • Le server affiche son PID avec getpid()
  • Le client reçoit ce PID en argument et l utilise dans kill(pid, sig)

§2.2 — Qu est-ce qu un signal UNIX ?

Un signal c est une notification asynchrone envoyée à un process. Asynchrone = elle peut arriver à n importe quel moment, sans que le process l attende explicitement.

★ Analogie de la sonnette
Imagine que tu sonnes chez ton voisin. Il sait que quelqu un est là, mais la sonnerie ne dit RIEN d autre — pas de contenu, juste une notification. Un signal UNIX c est pareil : uniquement un type, zéro contenu.

Linux a ~30 signaux prédéfinis, chacun avec un sens standard :

SignalSens
SIGINTCTRL+C dans le terminal — arrête-toi
SIGKILLkill -9 — meurs maintenant (non bloquable)
SIGTERMkill — termine proprement
SIGSEGVsegfault (accès mémoire invalide)
SIGUSR1libre pour usage perso
SIGUSR2libre pour usage perso

Le sujet impose qu on utilise uniquement SIGUSR1 et SIGUSR2. Ce sont les seuls signaux laissés libres pour des usages applicatifs perso.

§2.3 — Comment Linux livre un signal

Quand le client appelle kill(server_pid, SIGUSR1), il ne touche pas directement la RAM du server. C est le kernel Linux qui sert d intermédiaire.

CLIENT  ──kill(SERVER_PID, SIGUSR1)──>  KERNEL  ──delivers SIGUSR1──>  SERVER

Le kernel maintient pour chaque process une table des signaux pending — une liste des signaux reçus mais pas encore traités. Quand le process est ordonnancé (= sélectionné par le scheduler pour s exécuter), le kernel vérifie cette table et invoque le handler enregistré pour les signaux pending.

★ Le flux
  1. Process A appelle kill(B, SIGUSR1)
  2. Le kernel met le bit SIGUSR1 à 1 dans la table pending de B
  3. Quand B est ordonnancé : kernel vérifie pending → SIGUSR1 actif → invoque le handler de B
  4. Le handler s exécute, B reprend ce qu il faisait

§2.4 — Le problème : pas de queue

Linux ne fait PAS la queue des signaux du même type. La table pending utilise un bit par signal, pas un compteur. Si SIGUSR1 est déjà pending pour le server, un 2ème SIGUSR1 qui arrive est ignoré (le bit est déjà à 1).

★ Conséquence pour minitalk
Si le client envoie 2 SIGUSR1 trop vite (avant que le server ait pu traiter le premier), le 2ème est perdu. On perd un bit, et tous les caractères suivants sont décalés et corrompus.

C est pour ça qu on utilise usleep(700) côté client après chaque signal — on laisse au server le temps de traiter le signal pending avant d en envoyer un autre.

§2.5 — Le handler de signal

Pour recevoir un signal, un process doit enregistrer un handler — une fonction qui sera appelée automatiquement par le kernel à la réception.

Il y a 2 APIs :

signal()sigaction()
Legacy POSIX. Comportement varie selon les UNIX. Sur certains systèmes le handler est reset après chaque signal (donc il faut le rappeler à chaque fois). Moderne POSIX. Comportement déterministe et portable. Permet de configurer un masque de signaux, des flags, et récupérer le PID du sender. À privilégier.

On utilise sigaction() dans notre code.

★ Le handler est spécial
Le handler s exécute dans un contexte d interruption. Il peut interrompre n importe quel code en cours (boucle, write, malloc...). Donc :
  • Doit être court — fais le minimum dedans
  • Doit utiliser uniquement des fonctions async-signal-safe (write OK, printf NON, malloc NON)
  • Variables modifiées dedans doivent être volatile sig_atomic_t pour la sécurité (recommandé)

§2.6 — Récap

★ À retenir
  • Un process a un PID unique pour l identifier
  • Un signal est une notification asynchrone sans contenu
  • Le kernel sert d intermédiaire pour livrer les signaux
  • Linux ne queue pas les signaux du même type (1 bit pending par signal)
  • SIGUSR1 et SIGUSR2 sont les 2 seuls signaux libres pour usage perso
  • Pour recevoir un signal, on enregistre un handler via sigaction
  • Le handler doit être court et async-signal-safe

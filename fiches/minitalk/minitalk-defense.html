1. Le projet en 1 minute

Deux programmes (client + server) qui se parlent uniquement via des signaux UNIX. Le client envoie une string au server bit par bit, le server reconstruit et affiche.

./client
PID + msg
→ kill(SIGUSR1/2) →
./server
affiche

Le protocole en 4 règles

SIGUSR1= bit 0
SIGUSR2= bit 1
8 signaux= 1 caractère (envoyés MSB first)
8 bits à 0 ('\0')= fin de message → server affiche '\n'
Pourquoi bit par bit ? On a seulement 2 signaux. Pour envoyer un caractère (0 à 255 en ASCII), il faut le décomposer en bits — c'est la seule façon d'utiliser 2 valeurs pour transmettre n'importe quelle donnée.

3. server.c décortiqué

3.1 handle_signal — le cœur du server

Appelée par le kernel à chaque signal reçu. Assemble les bits en char et affiche dès qu'on a 8 bits.

src/server.c — handle_signal
static void handle_signal(int sig) { static unsigned char c; static int bit_count; c = c << 1; // fait de la place à droite if (sig == SIGUSR2) c = c | 1; // met un 1 si SIGUSR2 bit_count++; if (bit_count == 8) { if (c == 0) write(1, "\n", 1); // fin de message else write(1, &c, 1); // affiche le char c = 0; bit_count = 0; } }
Les variables static : elles gardent leur valeur entre les appels du handler. Sans static, c et bit_count repartiraient à 0 à chaque signal et on perdrait l'état de reconstruction.
Auto-init à 0 : en C, une variable static non initialisée est automatiquement initialisée à 0 par le standard. Pas besoin d'écrire = 0.
Pourquoi unsigned char ? Avec un char signé, si le bit 7 est à 1 (caractères > 127), le shift gauche peut faire déborder vers le bit de signe — comportement indéfini en C. unsigned char garantit que tous les shifts sont prévisibles.

3.2 print_pid — affichage sans printf

src/server.c — print_pid
static void print_pid(void) { pid_t pid; char buf[12]; int i; pid = getpid(); i = 0; while (pid > 0) { buf[i++] = (pid % 10) + '0'; pid /= 10; } write(1, "Server PID: ", 12); while (i--) write(1, &buf[i], 1); write(1, "\n", 1); }
Pourquoi à l'envers ? La boucle remplit buf[] en partant des unités. Pour afficher dans le bon ordre, on parcourt le buffer en arrière avec while (i--).

3.3 main — setup + boucle pause

src/server.c — main
int main(void) { struct sigaction sa; print_pid(); sigemptyset(&sa.sa_mask); sigaddset(&sa.sa_mask, SIGUSR1); sigaddset(&sa.sa_mask, SIGUSR2); sa.sa_flags = SA_RESTART; sa.sa_handler = handle_signal; sigaction(SIGUSR1, &sa, NULL); sigaction(SIGUSR2, &sa, NULL); while (1) pause(); return (0); }
Pourquoi sigaddset les 2 signaux ? Quand le handler tourne, par défaut seul le signal qui l'a déclenché est bloqué. Avec sigaddset, on bloque AUSSI l'autre signal. Ça évite qu'un handler SIGUSR1 soit interrompu par un SIGUSR2 (race condition sur c et bit_count).
while (1) pause() : pause() bloque le process jusqu'à réception d'un signal. Quand le handler finit, pause() retourne et la boucle relance pause(). Le server attend ainsi indéfiniment.

4. client.c décortiqué

4.1 send_char — extraction et envoi des 8 bits

src/client.c — send_char
static void send_char(int pid, char c) { int i; unsigned char uc; uc = (unsigned char)c; i = 7; while (i >= 0) { if ((uc >> i) & 1) kill(pid, SIGUSR2); else kill(pid, SIGUSR1); usleep(700); i--; } }
(uc >> i) & 1 : formule magique pour extraire le bit à la position i.
• uc >> i : décale les bits de i positions vers la droite → le bit qui nous intéresse arrive en position 0
• & 1 : garde uniquement le bit 0, efface tout le reste → résultat = 0 ou 1
MSB first (i de 7 à 0) : on envoie le bit le plus à gauche en premier. Convention arbitraire mais cohérente avec la reconstruction côté server.
usleep(700) : sans ça, le client envoie les signaux trop vite et Linux en perd. 700µs laisse au server le temps de traiter chaque bit. Calibré pour rester sous "100 chars en 1 seconde" : 800 bits × 700µs ≈ 560ms.

4.2 check_pid — le ping kill(pid, 0)

src/client.c — check_pid
static int check_pid(int pid) { if (pid <= 0) return (0); if (kill(pid, 0) == -1) return (0); return (1); }
kill(pid, 0) : le signal 0 est spécial. Il ne déclenche AUCUN handler. Mais il fait les vérifications de permission.
• retourne 0 si le process existe et on peut lui parler ✅
• retourne -1 si le PID n'existe pas (ESRCH) ❌
• retourne -1 si on n'a pas le droit (EPERM) ❌
C'est l'idiome standard pour valider un PID.

4.3 main — validation + boucle envoi

src/client.c — main
int main(int argc, char **argv) { int pid; int i; if (argc != 3) return (write(2, "Usage...\n", 32), 1); pid = atoi(argv[1]); if (!check_pid(pid)) return (write(2, "Error...\n", 34), 1); i = 0; while (argv[2][i]) send_char(pid, argv[2][i++]); send_char(pid, '\0'); return (0); }
send_char(pid, '\0') à la fin : envoie 8 bits à 0. Côté server, quand c == 0 au moment du bit_count == 8, le server affiche '\n'.
Pattern return (write(...), 1) : opérateur virgule pour écrire le message d'erreur ET retourner 1 en une seule expression. Norm-friendly.

5. Le Makefile

Makefile
NAME = server client CC = cc CFLAGS = -Wall -Wextra -Werror -I includes OBJS = src/server.o src/client.o all: $(NAME) $(NAME): %: src/%.o $(CC) $(CFLAGS) -o $@ $< src/%.o: src/%.c includes/minitalk.h $(CC) $(CFLAGS) -c $< -o $@ clean: rm -f $(OBJS) fclean: clean rm -f $(NAME) re: fclean all .PHONY: all clean fclean re
Static pattern rule $(NAME): %: src/%.o : pour chaque nom dans $(NAME) ("server" et "client"), Make génère une règle qui compile à partir du .o correspondant. Évite de répéter la règle 2 fois.
Pas de relinking inutile : la dépendance src/%.o: src/%.c $(HEADER) force la recompilation uniquement si le .c ou le header a changé.

6. Concepts à maîtriser

6.1 Le binaire — un char = 8 bits

Un char en C est un nombre entier sur 8 bits, soit 0 à 255 (en unsigned).

'S' = 83 = 64 + 16 + 2 + 1 = 01010011

6.2 Les opérations bit

OpérateurEffetExemple
a >> ndécale à droite (÷ 2^n)83 >> 1 = 41
a << ndécale à gauche (× 2^n)41 << 1 = 82
a & bAND bit à bit83 & 1 = 1
a | bOR bit à bit0 | 1 = 1
Les 2 formules à retenir :
• (c >> i) & 1 → extrait le bit à la position i (client)
• (c << 1) | bit → ajoute un bit à droite (server)

6.3 Les fonctions signaux

FonctionRôle
kill(pid, sig)envoie sig à pid. Malgré le nom, ça ne tue pas forcément.
sigaction(sig, &sa, NULL)enregistre le handler sa pour sig
sigemptyset(&set)vide le set de signaux
sigaddset(&set, sig)ajoute sig au set
pause()bloque jusqu'à un signal
getpid()retourne le PID courant

6.4 struct sigaction — les 3 champs

  • sa_handler : pointeur vers la fonction handler (signature void f(int))
  • sa_mask : ensemble des signaux à bloquer pendant l'exécution du handler
  • sa_flags : options (ex: SA_RESTART pour restart les syscalls interrompus)

6.5 Pourquoi usleep et pas ACK ?

Linux ne fait pas la queue des signaux. Si 2 SIGUSR1 arrivent trop vite, le 2ème est ignoré. Solution mandatory : usleep(700) entre chaque bit. Solution bonus : ACK explicite du server.

6.6 Pourquoi unsigned char ?

Le shift droit sur un char signé avec bit haut à 1 est comportement indéfini en C. unsigned char garantit que le shift introduit des 0 à gauche (logique pure).

6.7 static dans le handler

  • garde sa valeur entre les appels de la fonction
  • auto-init à 0 par le standard C
  • n'est pas une variable globale (donc ne compte pas dans la limite du sujet)

7. FAQ defense — questions piège

Pourquoi unsigned char et pas char ?
Parce que le shift droit sur un char signé avec bit haut à 1 a un comportement indéfini en C. unsigned char garantit que les shifts se comportent comme on s'y attend.
Pourquoi MSB first et pas LSB first ?
C'est une convention arbitraire. Ce qui compte c'est que client et server soient d'accord. MSB first c'est plus intuitif quand on lit le binaire (de gauche à droite).
Comment ça marche si plusieurs clients envoient en même temps ?
Le sujet dit "plusieurs clients in a row" — séquentiellement, pas en parallèle. Si plusieurs envoient simultanément, les bits se mélangent et le résultat est corrompu. C'est hors scope du mandatory.
Que se passe-t-il si le server crash en cours de message ?
Le client continue à envoyer, mais comme le PID n'existe plus, les kill() retournent -1 et les signaux sont perdus. Pour gérer ça parfaitement, il faudrait checker la valeur de retour de kill() dans send_char.
Pourquoi usleep(700) et pas 100 ou 5000 ?
Trade-off vitesse / fiabilité. Trop court = signaux perdus. Trop long = trop lent (sujet : 100 chars en moins d'1 seconde). 700 donne le meilleur compromis : ~676ms pour 100 chars avec 90%+ de fiabilité.
Pourquoi sa_handler et pas sa_sigaction avec SA_SIGINFO ?
SA_SIGINFO permet de récupérer le PID du sender via siginfo_t. Utile pour répondre au client (bonus ACK), mais pour mandatory pur on n'en a pas besoin. sa_handler suffit.
Pourquoi sigaddset les 2 signaux dans sa_mask ?
Par défaut, seul le signal traité est bloqué pendant le handler. Mais nos 2 signaux modifient les mêmes variables statiques. Sans sigaddset, un SIGUSR2 pourrait interrompre un handler SIGUSR1 et corrompre la reconstruction. On bloque les 2 pour atomiser l'opération.
Comment le server sait que le message est fini ?
Le client envoie '\0' à la fin (8 bits à 0). Quand le server reconstruit un caractère c == 0, il affiche '\n'. C'est le marqueur de fin convenu.
Et si le PID est négatif ou 0 ?
check_pid retourne 0 dans ces cas. On évite ainsi kill(0, ...) qui enverrait le signal au process group entier — dangereux.
Le sujet autorise 1 global, tu en utilises 0 — est-ce un problème ?
Non, c'est même mieux. Le sujet dit "max 1 global, justifiée". Si on peut s'en passer (en utilisant static locales), c'est plus propre. Pas de pollution du namespace global.
Linux ne fait pas la queue des signaux, comment tu gères ?
Avec usleep(700) côté client entre chaque bit. Le server a le temps de traiter avant que le suivant arrive. Le bonus serait un ACK explicite, mais c'est hors scope mandatory.
Comment marcherait Unicode (bonus) ?
UTF-8 encode chaque caractère sur 1 à 4 bytes. Comme on traite déjà en unsigned char byte par byte, Unicode juste marche — le client envoie les bytes UTF-8 dans l'ordre, le server les reconstruit dans l'ordre. Aucune modification nécessaire.
Tu n'as pas implémenté l'ACK serveur → client, c'est obligatoire ?
Non, c'est bonus. Le sujet bonus dit "The server must acknowledge each received message". C'est un ACK par message complet, pas par bit. Pour mandatory, usleep suffit.
Pourquoi SA_RESTART ?
Pour redémarrer automatiquement les syscalls interrompus par un signal. pause() est conçu pour retourner sur signal (pas restartable), donc SA_RESTART n'a pas d'effet ici. C'est défensif — sans effet négatif.
Comment tu valides ton code ? (tests, norm, leaks)
• norminette : 3/3 fichiers OK
• compile : 0 warning avec -Wall -Wextra -Werror
• leaks : pas de malloc = pas de leak possible
• timing : 100 chars en 676ms (limite 1000ms)
• edge cases : argc != 3, PID invalide, string vide, plusieurs messages
